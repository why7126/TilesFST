# 临时规避方案

在正式修复完成前，可使用以下临时规避方式降低用户可见影响。

## 方案一：清空缺失头像字段

对已确认对象缺失的用户记录，将 `avatar_object_key` 清空，使资料接口返回空头像并由前端显示 initials。

适用条件：

- 无法找回原头像对象。
- 当前环境优先保证管理后台不再请求缺失媒体 URL。
- 已确认操作对象为演示数据或可修复的内部账号数据。

风险：

- 会丢失原头像引用。
- 需要在执行前确认目标账号范围，避免误清真实用户数据。

## 方案二：补齐对象存储文件

如果能够从备份、历史上传目录或对象存储版本中找回原头像文件，可将文件补回原 `avatar_object_key` 对应位置。

适用条件：

- 原头像有恢复价值。
- 能确认补回对象与该用户头像字段匹配。

风险：

- 如果补错对象，会造成用户头像错配。
- 只能修复当前数据，不会阻止后续写入不存在 key。

## 方案三：用户重新上传头像

由受影响用户在个人资料页重新上传头像，并保存新上传返回的 `object_key`。

适用条件：

- 用户可接受重新上传。
- 上传链路当前可用。

风险：

- 当前后端仍可能接受不存在的 key；正式修复前仍缺少写入侧防护。

# 推荐临时处理

本 BUG 推荐优先采用“清空确认缺失的头像字段”作为临时止血，并在正式修复中补齐后端写入校验和前端展示兜底。若原头像对象可找回，再选择补齐对象。

# 不建议方案

不建议使用统一占位图片写回所有缺失 `avatar_object_key`。这会把数据漂移伪装成正常头像，降低后续审计和修复可见性。
