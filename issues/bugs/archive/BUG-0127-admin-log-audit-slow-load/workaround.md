# 临时规避方案

## 可用规避

在正式修复前，可通过以下方式缓解管理后台日志审计加载慢的问题：

1. 优先使用更短时间范围排查，例如最近 5 分钟、30 分钟或 1 小时，减少参与计数和排序的数据量。
2. 已知 request_id 或 Task Trace ID 时，直接使用精确筛选，避免先打开宽范围列表再人工查找。
3. 生产排障时优先通过后端日志、数据库只读查询或慢查询日志定位单次请求，管理端日志审计页作为辅助入口。
4. 在低峰期执行日志审计的大范围查询，避免高峰期与业务请求争抢数据库资源。
5. 运维侧可评估日志保留策略，避免超出业务要求的历史日志无限增长；任何清理策略必须先经过 OpenSpec Change 并保留审计合规边界。

## 不建议的规避

- 不建议关闭请求日志、行为事件或审计日志记录；这会削弱排障、审计和安全追踪能力。
- 不建议绕过系统鉴权直接暴露日志表查询入口。
- 不建议在生产库上执行无时间范围、无索引命中的临时大查询。
- 不建议只把前端默认时间范围缩短就视为修复完成；这只能缓解首屏压力，不能解决查询形态和指标聚合问题。

## 剩余风险

临时规避无法解决日志表持续增长后的根本性能问题。若生产环境日志量继续增加，即使缩短默认时间范围，指定筛选、分页总数和摘要指标仍可能出现慢查询。正式修复仍需调整后端查询形态、指标加载策略和数据库索引。
