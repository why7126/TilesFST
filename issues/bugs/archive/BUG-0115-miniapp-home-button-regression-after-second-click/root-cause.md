# 直接原因

小程序返回首页悬浮按钮在一次成功导航后，后续再次进入页面时仍可能保留不可点击或已导航中的状态，导致第二次点击无法再次触发有效的首页跳转。

当前代码中统一组件已包含 `navigating` 防重复锁、800ms 延迟解锁、`pageLifetimes.show()` 重置和 `reLaunch` 兜底，但用户反馈表明真实运行环境中仍存在第二次点击失效路径。直接原因需要在真机或微信开发者工具中确认具体落点，重点怀疑导航锁释放时机、组件生命周期触发、跨 TabBar 页面复用状态或小程序运行时对 `switchTab` 成功回调的处理差异。

# 根本原因

返回首页按钮属于全局导航辅助能力，但历史修复后的回归保护仍偏静态：

- 现有测试主要断言源码中存在解锁、兜底和页面 show 重置逻辑，未模拟“进入页面 → 点击返回首页 → 再次进入页面 → 第二次点击”的真实组件状态流。
- TabBar 页面、非 TabBar 详情页、搜索结果页等页面的生命周期与页面栈行为不同，仅凭统一组件代码无法证明所有页面都能重复恢复。
- 历史 BUG-0109 已修复并归档，但本次反馈与旧现象一致，说明验收或自动化覆盖没有稳定守住回归场景。
- 若 `switchTab` 成功后原页面组件未按预期触发延迟解锁或再次 show 重置，`navigating` 锁可能在部分页面实例中残留。

# 触发条件

1. 用户进入带返回首页悬浮按钮的非首页页面。
2. 用户第一次点击返回首页按钮，页面通过 `switchTab` 或兜底方式回到首页。
3. 用户再次进入同一页面，或进入另一个带返回首页按钮的页面。
4. 返回首页组件未完成导航锁释放，或新页面实例/旧页面实例继承了不可点击状态。
5. 用户第二次点击返回首页按钮时，点击处理被 `navigating` 状态拦截，或导航 API 未再次执行。

# 需验证线索

- `home-floating-button` 的 `navigating` 是否在每次点击后都会恢复为 `false`。
- `pageLifetimes.show()` 是否在 TabBar 页面、详情页、搜索结果页等覆盖场景中稳定触发。
- `wx.switchTab` 成功、失败和完成路径是否都能释放锁；失败后 `wx.reLaunch` 的 `complete` 是否被执行。
- 快速重复点击是否只阻止短时间内的重复导航，而不会影响下一轮正常点击。
- 当前体验版或真机运行包是否包含最新的 BUG-0109 修复代码，是否存在运行入口未同步或上传版本滞后。
