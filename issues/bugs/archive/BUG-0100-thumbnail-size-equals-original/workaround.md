# 临时规避方案

## 当前可用规避

在正式修复前，系统没有真正降低 `.thumb` 对象尺寸的自动规避方案。可采用以下临时措施降低影响：

1. 对公开 SKU 主图和 `.thumb` 对象做只读审计，统计原图大小、缩略图大小、相同 size 或相同 bytes 的数量。
2. 对首屏和高流量商品优先人工重生成缩略图，再通过后端对象存储适配层写回同目录 `.thumb` key。
3. 在修复前避免把“缩略图对象存在”作为性能优化已生效的判断依据。
4. 保留公开端已有 `lazy-load`、图片缓存头和缺图 fallback，避免因为缩略图失效进一步放大首屏压力。
5. 若移动端加载压力明显，可临时减少列表首屏数量或优先展示已人工处理缩略图的商品。

## 不建议的规避

- 不建议让前端或小程序直连对象存储生成或读取非后端授权 URL。
- 不建议继续运行“复制原图到 `.thumb`”作为本缺陷的修复方式；该方式只能解决对象缺失，不能解决尺寸与体积问题。
- 不建议直接删除全部 `.thumb` 对象迫使媒体读取回退原图；这会让公开列表明确退回原图加载。
- 不建议只通过 CSS 或小程序 `mode` 缩小展示尺寸；展示尺寸变小不等于网络传输体积下降。
- 不建议在未验证透明图和小图策略前批量强制转 JPG。

## 存量数据规避

对已存在的 `.thumb` 对象：

- 先 dry-run 输出疑似无效缩略图清单，包括 SKU、原图 key、缩略图 key、原图 size、缩略图 size 和判断原因。
- 对确认需要处理的对象执行重生成，而不是复制原图。
- 重生成过程必须可重入，失败时保留原对象或明确记录失败原因。
- 输出不得包含密钥、Authorization header、Cookie、`.env` 内容或本机路径。

## 限制

以上规避只能降低部分公开入口的加载成本，不能从根本上保证后续新增上传都生成有效缩略图。根治仍需要在后端媒体处理链路中加入真实图片派生能力，并补齐历史对象重生成策略。
