# 现象

当前生成的缩略图大小与原图大小一样，导致缩略图没有体现降低加载成本的意义。

# 复现步骤

1. 上传或查看已有商品图片。
2. 找到原图与对应缩略图对象。
3. 对比两者的像素尺寸、文件体积和访问 URL。
4. 观察缩略图是否与原图尺寸一致，且列表或卡片场景是否仍加载近似原图体积的资源。

# 期望 vs 实际

- 期望：缩略图应按列表、卡片、预览等场景生成较小尺寸和体积的派生图，用于提升 Web 与小程序商品图片加载速度。
- 实际：缩略图尺寸与原图相同，文件体积可能没有有效下降，无法发挥缩略图优化价值。

# 影响范围

- 后端媒体处理与缩略图生成逻辑。
- 店主 Web 展示端与微信小程序商品列表、商品卡片、详情页预览图加载性能。
- 对象存储容量、流量消耗和移动端体验。
- 可能影响此前针对商品卡片图片加载慢的优化效果。

# 初步线索

- 需要确认缩略图生成是否只复制原图或只改 key/格式，未做 resize/compress。
- 需要明确不同场景的缩略图目标尺寸、质量、格式和最大体积约束。
- 需要检查已有缩略图是否需要重生成，以及重生成过程中是否保留旧 URL 兼容。
- 修复应集中在 media 模块和对象存储适配层，避免前端直连对象存储或各端重复处理。

# 建议验收或复现要点

- [ ] 新生成缩略图的像素尺寸小于原图，并符合约定的最大宽高。
- [ ] 新生成缩略图的文件体积通常小于原图，且不会因格式转换异常反而增大。
- [ ] 商品列表、卡片和预览场景优先使用缩略图 URL，详情大图仍可使用原图或高清图。
- [ ] 已有缩略图提供重生成、迁移或兼容策略。
- [ ] Web 与小程序图片加载速度不回退。
- [ ] 补充媒体处理测试，覆盖横图、竖图、大图、小图、透明图和异常图片输入。
