# 根因分析

## 直接原因

SKU 图片上传接口会为商品图片生成同目录 `.thumb` 缩略图 key，但底层保存函数在写入缩略图对象时直接复用原始上传内容。

`save_upload_file()` 在 `thumbnail_key` 存在时，将已经读取的原图 `content` 原样写入缩略图对象，没有执行图片解码、resize、重编码、压缩或尺寸上限控制。因此 `.thumb` 对象只是原图的复制品，像素尺寸、文件体积和内容 bytes 可能与原图完全一致。

历史商品卡片图片审计回填脚本也采用相同思路：发现缩略图对象缺失时，将原图 bytes 直接复制到 `.thumb` key。这会补齐“缩略图对象存在性”，但不会补齐“缩略图真实派生处理”。

## 根本原因

媒体链路把“生成缩略图 key 并保证对象存在”误当成“生成有效缩略图”，缺少真实缩略图处理契约和验收门禁：

- 上传接口已经区分原图 key 与 `.thumb` key，但没有定义缩略图目标最大宽高、质量、格式和透明图处理策略。
- 媒体存储模块只负责对象写入，没有封装图片派生处理函数。
- 历史回填脚本只验证原图与缩略图对象是否存在，没有验证缩略图尺寸或体积是否降低。
- 现有测试覆盖缩略图 key 规则、对象存在性、缺失回退和历史回填，但没有断言像素尺寸、文件体积或编码质量。
- 后端依赖当前未包含图片处理库，修复时需要明确引入依赖、异常降级和 Docker 镜像构建边界。

## 触发条件

满足以下条件时可稳定触发：

1. 管理端上传 SKU 商品图片。
2. 上传入口调用 `save_upload_file()` 并传入 `same_directory_thumbnail_object_key(object_key)`。
3. 后端写入原图对象后继续写入 `.thumb` 对象。
4. 缩略图写入逻辑直接使用原始上传 bytes。
5. 公开商品卡片、商品列表、搜索结果或品牌详情商品区优先读取 `.thumb` URL。

## 缺陷分类

- `code`：缩略图写入逻辑缺少 resize、compress 和图片格式处理。
- `design`：媒体缩略图能力没有明确目标尺寸、质量、体积和失败策略。
- `test`：现有测试只覆盖对象存在性，没有覆盖“缩略图必须比原图更轻”的行为约束。
- `migration`：历史回填脚本会复制原图作为缩略图，存量 `.thumb` 对象可能需要重生成。

## 风险

- 公开端看似使用缩略图，实际仍加载原图体积，移动端首屏和列表滚动性能收益不足。
- 对象存储中同时保存原图和同内容缩略图，增加存储容量与流量成本。
- 如果后续只修新增上传，不处理历史 `.thumb` 对象，存量公开商品卡片仍可能继续加载大图。
- 如果修复时仅强制转换格式，可能导致透明 PNG/WebP 失真或小图被放大。
- 如果缩略图生成失败后中断原图上传，可能影响管理端上传主流程，需要定义失败降级策略。

## 已确认结论

- 已确认：SKU 图片上传会传入同目录 `.thumb` 缩略图 key。
- 已确认：当前保存函数把原图 bytes 原样写入缩略图 key。
- 已确认：临时复现脚本中原图与缩略图 `same_bytes=True`，对象 size 相同。
- 已确认：历史回填脚本也通过复制原图补齐缩略图对象。
- 已确认：现有相关测试通过，但没有覆盖缩略图尺寸或体积下降。

## 修复策略边界

| 事项 | 结论 | 说明 |
|---|---|---|
| 缩略图命名 | 继续使用同目录 `.thumb` key | 与既有 BUG-0094 媒体 URL 契约保持一致。 |
| 生成位置 | 后端媒体链路 | 前端不得直连对象存储或自行生成对象 key。 |
| 失败策略 | 需在 Change 中明确 | 可考虑原图上传成功、缩略图生成失败时记录告警并回退原图读取。 |
| 历史数据 | 需要审计与重生成策略 | 只补对象存在性不足以关闭本缺陷。 |
| 依赖变化 | 可能需要新增图片处理库 | 需同步 Docker 构建与测试验证。 |

- 补充上传链路、历史回填和媒体读取相关测试。
- 设计历史 `.thumb` 对象重生成脚本的 dry-run / apply 输出格式。
