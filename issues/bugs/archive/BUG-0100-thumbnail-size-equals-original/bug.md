# 现象

SKU 商品图片上传后会生成同目录 `.thumb` 缩略图对象，但当前缩略图对象与原图内容一致，无法体现降尺寸、降体积和加速加载的效果。商品列表、商品卡片、搜索结果、品牌详情商品区等公开展示场景优先使用缩略图 URL 时，仍可能加载近似原图体积的资源。

# 复现

1. 通过管理端 SKU 图片上传接口上传一张商品图片。
2. 获取接口返回的原图 `object_key`，并按同目录 `.thumb` 规则定位缩略图 key，例如 `images/default/tiles/pending/<uuid>.jpg` 对应 `images/default/tiles/pending/<uuid>.thumb.jpg`。
3. 分别读取原图对象和缩略图对象。
4. 对比两者的像素尺寸、文件体积或对象 bytes。

当前探索阶段已用内存对象存储调用 `save_upload_file()` 复现：原图 key 与缩略图 key 写入后 `same_bytes=True`，两者 size 相同。源码层直接证据是 `save_upload_file()` 在 `thumbnail_key` 存在时，将同一份 `content` 原样写入缩略图对象；历史审计回填脚本也将原图 bytes 原样复制到 `.thumb` key。

# 期望 / 实际

期望：

- 缩略图应作为真实派生图生成，像素尺寸小于原图，并符合商品列表、卡片或预览场景约定的最大宽高。
- 缩略图文件体积通常应小于原图，且不应因格式处理异常明显增大。
- 公开列表和小程序商品卡片继续优先使用缩略图 URL，详情大图仍可使用原图或高清图。
- 历史缩略图应有可审计、可重入的重生成或迁移策略。

实际：

- SKU 图片上传链路只创建 `.thumb` key，但内容与原图完全一致。
- 历史回填脚本只补齐缩略图对象存在性，同样没有 resize 或 compress。
- 现有相关测试覆盖缩略图 key、对象存在性和回退行为，但没有断言像素尺寸或文件体积下降。

# 影响范围

- 后端媒体处理模块与对象存储适配层。
- 管理端 SKU 图片上传后生成的缩略图对象。
- 小程序首页、商品列表、搜索结果、品牌详情商品区等商品卡片图片加载性能。
- 店主 Web 展示端中复用商品卡片或缩略图 URL 的页面。
- 对象存储容量、外网流量与移动端首屏体验。
- 此前商品卡片图片加载慢相关优化的实际收益。

# 严重等级说明

严重等级为 `high`。该问题不直接导致上传失败或图片不可见，但会让缩略图优化名义上存在、实际性能收益缺失，影响公开商品浏览核心路径，并可能持续增加对象存储容量和移动端流量成本。由于该问题位于后端统一媒体链路，一次缺陷可能扩散到多个前端展示入口。

# 初步范围建议

后续 `/bug-complete` 阶段需进一步补齐根因、临时绕行与验收标准，重点确认：

- 缩略图生成目标尺寸、质量、格式和透明图处理策略。
- 小图是否跳过放大或仅压缩。
- JPG、PNG、WebP、横图、竖图、大图、异常图片输入的测试覆盖。
- 历史 `.thumb` 对象是否需要重生成，以及重生成是否保持 URL 兼容。
- 是否需要新增图片处理依赖并同步 Docker 镜像构建验证。
