# 现象

用户反馈：opsx-apply 在仍有已授权、依赖满足的独立任务时提前结束，必须反复调用或发送“继续”才能推进。影响 Change 连续交付效率和验收进度可信度。

五项修复重点属于同一次 apply 执行与收尾的行为契约，按一条缺陷记录，通过统一行为场景闭环；不据此推定共同根因已经确认。

# 复现步骤

以下为基于用户反馈整理的复现方案，尚未实际执行：

1. 对已纳入 Sprint、已授权实施且包含多个独立任务的 Change 调用 opsx-apply。
2. 执行部分任务后，保留至少一个依赖满足且无新增授权要求的任务；观察是否提前发出最终回复。
3. 分别触发首次测试失败、单项人工或外部阻塞，以及执行期间用户询问进度。
4. 记录每次是否继续独立工作、是否需要用户再次发送“继续”，以及剩余任务、阻塞项和工具重试的处理过程。

# 期望 vs 实际

期望：一次授权后持续推进可执行工作，使用中间消息汇报进度；必要人工确认一次集中收集并说明具体阻塞项。

实际：用户反馈部分工作完成后即结束，需要重复调用才能推进。具体任务编号、失败工具及完整执行证据尚未提供，其他场景作为待验证的修复要求，不宣称已复现。

# 修复重点与建议验收

| 场景 | 建议验收要点 |
|---|---|
| 收尾前检查 | 每次准备最终回复前检查剩余任务的授权、依赖和阻塞条件；还有可执行工作即继续。全部完成或所有剩余工作均有明确阻塞时，才收尾并逐项说明原因。 |
| 人工问题集中收集 | 承接已有确认，集中提出当前已知问题，标明每个答案阻塞哪一项；等待期间推进独立任务。仅在出现新事实时补问，不重复请求既有授权。 |
| 验收进度分层 | 分别展示实现完成、自动验证通过、人工待验、外部阻塞；保留完整验收要求、证据入口和未通过项，不以实现完成代替全部验收通过，不提前发出完成事件。 |
| 限制无效重试 | 为连续同类工具失败设置有限重试策略，记录次数、失败摘要及受阻任务，达到上限后切换独立任务；只有新输入、环境变化或修复证据时才恢复重试。具体阈值在后续方案中明确。 |
| 首次测试失败 | 在实际执行中注入可恢复测试失败，观察自主定位、修复、重跑相关验证并继续后续任务，全程不需要用户发送“继续”。 |
| 单项阻塞 | 设置任务 A 等待人工或外部条件、任务 B 独立可执行；观察集中说明 A 的阻塞并继续完成 B，不越过 A 的确认边界。 |
| 用户询问进度 | 执行期间询问进度，观察中间消息回答后继续执行当前已授权任务；用户明确要求停止时按其要求停止。 |
| 行为证据 | 三个核心场景保留脱敏的运行标识、任务顺序、工具结果摘要、时间及最终状态；只检查技能或规则中的关键词不能作为行为验收通过依据。 |
