# Root Cause

## 直接原因

小程序 SKU 详情页内嵌视频播放与右上角全屏入口使用了不同的播放路径：内嵌态由页面中的 `<video>` 组件播放，用户点击自定义全屏入口后进入独立媒体预览链路。

内嵌 `<video>` 已经完成加载并可播放时，独立预览链路仍可能重新对同一个视频 URL 发起媒体探测、拉流和缓冲，未复用当前 `<video>` 组件已经建立的播放上下文与缓存状态，因此表现为“全屏前能播，全屏后重新加载很久”。

## 根本原因

视频全屏交互设计把“进入全屏播放”和“打开媒体预览器”混为同一条用户路径，导致全屏入口没有优先复用当前正在播放的视频组件上下文。

当前能力缺少针对以下场景的显式验收约束：

- 内嵌视频已播放成功后切换全屏的首帧耗时。
- 全屏入口是否复用当前 `<video>` / `VideoContext`。
- 独立预览链路是否会重新加载已播放视频。
- 真机环境下内嵌播放与全屏播放的加载耗时对比。

## 触发条件

- SKU 详情页存在视频媒体项。
- 用户先在详情页内嵌轮播区域播放视频，且视频已经开始播放。
- 用户点击视频右上角自定义全屏入口。
- 全屏入口进入独立媒体预览链路，或等价地未复用当前视频上下文。
- 网络、视频大小、编码、对象存储链路或预览器重新探测机制使全屏态重新加载耗时明显。

## 待验证项

- 真机记录同一 SKU 视频内嵌播放首帧耗时与点击全屏后的首帧耗时。
- 验证全屏入口是否调用独立媒体预览能力，还是当前 `VideoContext` 的全屏能力。
- 验证视频 `/media/{object_key}` Range/206 响应正常时，全屏切换是否仍重新长时间加载。
- 验证切换全屏前后是否产生新的媒体请求，尤其是从 0 字节重新探测或重新拉流。
