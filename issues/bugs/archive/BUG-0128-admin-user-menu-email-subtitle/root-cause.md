# Root Cause

## 直接原因

管理后台前端在身份展示区域把“邮箱展示兜底”写成了前端拼接逻辑：

- 用户菜单栏通过 `getUserEmail(user?.username, profileEmail)` 生成副标题。
- `getUserEmail()` 在邮箱为空时返回 `${username}@tilesfst.com`，无用户名时返回 `admin@tilesfst.com`。
- 个人资料页顶部身份栏使用 `profile.email?.trim() || `${profile.username}@tilesfst.com``，在邮箱为空时同样拼接伪邮箱。

因此，只要当前用户邮箱为空，界面仍会出现邮箱样式文本。

## 根本原因

资料字段语义和身份展示语义混在一起了：

- `email` 是真实联系邮箱，允许为空。
- 用户菜单栏需要展示的是当前账号身份标识，不需要邮箱副标题。
- 个人资料页顶部身份栏可以展示真实邮箱，但不应在邮箱为空时创造一个看似真实的邮箱。
- 旧测试把 `admin@tilesfst.com` 兜底当成预期，导致伪邮箱行为被固化。

## 触发条件

满足以下条件时稳定触发：

1. 当前后台用户的 `email` 字段为空。
2. 用户进入管理后台。
3. 查看左侧用户菜单栏，或进入个人资料页顶部身份栏。

## 分类

- 分类：`design`
- 影响层：Web 前端展示逻辑
- 不涉及：后端 API、数据库结构、小程序、对象存储、Orval 生成

## 修复边界

应纳入本 BUG：

- 用户菜单栏只显示昵称；昵称为空时显示用户名；不显示邮箱或副标题。
- 个人资料页顶部身份栏只显示真实邮箱；邮箱为空时省略邮箱片段或使用非误导性展示。
- 个人资料编辑页“联系邮箱”输入框保留，作为真实邮箱维护入口。
- 更新相关前端测试，移除伪邮箱兜底断言。

不纳入本 BUG：

- 用户管理页新增或编辑联系邮箱能力。
- 用户列表新增邮箱列。
- 邮箱唯一性、邮箱登录、邮箱验证等账号体系能力。
