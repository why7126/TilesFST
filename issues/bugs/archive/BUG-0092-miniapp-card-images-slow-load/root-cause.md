# 直接原因

小程序商品卡片图片加载链路对列表场景不够轻量。

当前首页会同时加载首页聚合数据和“全部产品”第一页，页面可能在首屏或近首屏一次性渲染 Banner、新品推荐、热销推荐和全部产品卡片。商品卡片组件直接使用后端返回的 `cover_image` 作为 `<image>` `src`，未见图片懒加载或首屏加载节流策略。

后端 `cover_image` 返回 `/media/{object_key}` 受控读取地址。该地址由后端从对象存储读取媒体对象后返回给小程序；当前列表卡片没有专用缩略图字段，也未见 `/media` 图片缓存头和媒体读取耗时日志。因此当体验版商品数量较多、图片偏大、对象存储响应慢或网络链路质量不稳定时，卡片图片会长时间排队、逐张补齐或加载失败。

# 根本原因

商品卡片能力在设计上复用了“原始媒体受控读取”链路，但没有为小程序列表页建立独立的图片性能契约：

- 没有区分列表缩略图、详情图和原图。
- 没有为卡片图定义目标尺寸、目标体积、格式、缓存策略和降级策略。
- 小程序卡片组件缺少 lazy-load / 按可见性加载策略。
- 后端 `/media` 读取链路默认排除请求日志，缺少单图耗时、失败率和对象缺失观测。
- 数据库 `tile_images.object_key` 与对象存储对象一致性缺少体验版上线前校验，存在主图引用缺失或迁移残留 key 的风险。

# 触发条件

1. 微信小程序体验版使用生产 API 地址。
2. 用户进入首页、商品列表页、品牌商品列表页或搜索结果页。
3. 页面一次性渲染多张商品卡片，且卡片均带有 `cover_image`。
4. `cover_image` 指向后端 `/media/{object_key}`，后端需从对象存储读取图片对象。
5. 图片对象偏大、对象存储响应慢、网络质量不稳定、图片未命中缓存或数据库引用对象缺失时，现象更明显。

# 数据与观测线索

- 本地行为事件中存在较多 `product_card_image_failed` 记录，集中在首页 `new_products`、`hot_products`、`all_products` 模块。
- 本地 SQLite 中存在公开 SKU 主图对象缺失或无主图记录的情况；生产对象存储需用体验版环境继续核对。
- 后端请求日志当前排除 `/media/`，无法直接从管理端日志页看到每张图片读取耗时，需要补充网络面板、Nginx 日志、对象存储日志或受控媒体观测。

# 分类

- 类型：performance / stability / media
- 层级：微信小程序前端、后端媒体读取链路、对象存储数据一致性
- 数据风险：中，公开 SKU 主图引用可能缺失或指向迁移残留对象
- API 风险：中，若新增缩略图字段或调整媒体 URL 契约，需要同步 API 文档与小程序调用
- 回归风险：中，需覆盖首页、商品列表、品牌商品、搜索结果、详情页原图和图片失败兜底
