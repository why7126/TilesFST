# 现象

小程序商品列表页与搜索页仍可能产生偏多 `/api/v1/usage-events` 请求。BUG-0143 已治理启动阶段埋点请求放大，但验收或后续观察中仍需继续分析并治理以下剩余口径：

- 商品列表页可能同时存在列表曝光与商品卡曝光两套口径，导致同一批 SKU 在同一渲染上下文中被重复计入 usage-events。
- 搜索页输入过程可能对每次输入变化、联想或搜索请求逐次上报，导致 usage-events 随键入频率放大。
- 曝光事件缺少跨列表、跨搜索结果刷新或跨页面生命周期的稳定去重策略，同一 SKU、同一模块、同一会话窗口内可能重复上报。

# 复现步骤

1. 启动本地后端服务与微信小程序开发环境。
2. 打开微信开发者工具网络面板，过滤 `/api/v1/usage-events`。
3. 进入商品列表页，滚动、切换筛选或刷新列表，观察列表曝光与商品卡曝光事件数量。
4. 进入搜索页，连续输入关键词、删除关键词、触发搜索联想或搜索结果刷新，观察 usage-events 请求数量。
5. 对比页面实际可见 SKU 数、搜索提交次数和 usage-events 事件数，确认是否存在重复口径或高频输入逐次上报。

# 期望 vs 实际

- 期望：列表页曝光口径唯一或有明确层级边界，同一 SKU 在同一模块、同一列表实例、同一曝光窗口内只上报一次；搜索输入过程应通过防抖、合并、采样或仅关键行为上报控制频率；曝光去重策略应覆盖商品列表页与搜索页。
- 实际：仍可能出现列表曝光双口径、搜索输入高频上报和曝光事件重复计入，使 usage-events 数量高于真实用户行为规模。

# 影响范围

- 微信小程序商品列表页、搜索页、商品卡组件和列表曝光逻辑。
- `/api/v1/usage-events` 行为埋点数据质量与后端写入量。
- BUG-0143 对埋点请求放大的修复验收边界。
- 后续商品曝光、搜索转化、热门商品和行为分析报表口径。

# 建议验收或复现要点

- [ ] 商品列表页仅保留一套可解释的列表曝光口径，或列表曝光与商品卡曝光具备互斥/层级边界，避免同一 SKU 双报。
- [ ] 搜索页输入过程不会按每个字符变化直接产生 usage-events；连续输入应合并为可控数量，或仅在搜索提交、结果展示等关键行为上报。
- [ ] 曝光事件具备稳定去重键，至少覆盖页面、模块、SKU、列表实例或搜索上下文、时间窗口等必要维度。
- [ ] 列表刷新、分页、筛选变化、搜索结果切换时，去重窗口可解释，不误杀新的真实曝光，也不重复上报旧曝光。
- [ ] 埋点失败仍不阻断商品列表浏览、搜索输入、搜索结果展示、商品点击或分享。
