# 用户故事

## US-001 系统管理员按任务链路追溯审计操作

作为系统管理员，我希望审计日志中的敏感操作能显示 `task_trace_id` 和 `task_type`，以便从一次审计操作进入完整任务链路。

验收要点：

- 审计日志列表能展示或搜索 `task_trace_id`。
- 审计日志详情能展示任务类型、任务状态和任务时间线入口。
- 没有关联 Task Trace 的审计日志仍按现有详情展示。

## US-002 安全审计负责人追溯关键操作上下文

作为安全 / 审计负责人，我希望系统设置、证书、媒体等关键操作在审计记录中保留任务上下文，以便确认操作者、资源、结果和关联主请求。

验收要点：

- 首批敏感操作清单在需求或 OpenSpec design 中明确。
- 审计 metadata 已脱敏，不保存密钥、Cookie、Authorization 或内部绝对路径。
- 同一次任务产生多条审计操作时，应共享同一个 `task_trace_id`。

## US-003 开发 / 运维从审计日志定位后台任务

作为开发 / 运维人员，我希望能从审计日志中的 `task_trace_id` 反查 Task Trace 节点，以便定位操作失败、耗时和关联请求。

验收要点：

- 审计日志写入接口可接收并持久化 `task_trace_id`、`task_type`。
- 详情中可查看关联 `request_id` 或父请求线索。
- 查询路径使用结构化字段和索引，不依赖 metadata 无界模糊搜索。

## US-004 企业内部运营理解操作结果

作为企业内部运营人员，我希望系统能在后台多步骤操作后留下可解释的审计事实源，以便减少重复提交和人工询问。

验收要点：

- 成功、失败或部分失败的敏感操作均有审计摘要。
- 任务型操作能关联任务状态和关键节点。
- 非任务型操作保持现有审计记录，不强制生成任务链路。

## US-005 产品负责人控制审计链路增强范围

作为产品负责人，我希望本需求只补齐审计日志与 Task Trace 的关联字段和展示，不扩大为全量任务型接口治理，以便控制交付边界。

验收要点：

- 全量任务型接口覆盖由 `REQ-0074-task-trace-coverage-expansion` 承接。
- 主请求、子请求强关联模型由 `REQ-0073-task-trace-parent-request-model` 承接。
- 本需求不创建独立审计页面，不回填历史审计数据。
