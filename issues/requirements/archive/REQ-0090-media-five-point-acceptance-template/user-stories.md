# User Stories

## US-001 产品负责人使用五联模板确认媒体能力闭环

作为产品负责人，我希望每个媒体相关需求都能按 key、object、URL、thumbnail benefit、miniapp render 五个维度验收，以便确认媒体能力不是只在某一端局部可用。

验收要点：

- [ ] 模板明确五个维度的检查目标、通过标准和证据字段。
- [ ] 每个维度都支持 `pass`、`fail`、`n/a`、`blocked` 状态。
- [ ] `n/a` 和 `blocked` 必须填写原因，不能空置。

## US-002 测试人员使用模板执行媒体回归

作为测试人员，我希望五联模板能直接转化为检查清单，以便在 Sprint 验收、发布前检查或缺陷回归时快速覆盖媒体链路。

验收要点：

- [ ] 模板可嵌入 `acceptance.md` 或验收报告。
- [ ] 模板支持一次记录多个媒体样例，且每个样例能独立追踪。
- [ ] 失败项能直接支撑后续 `/bug-capture` 输入。

## US-003 开发人员使用模板定位媒体链路问题

作为开发人员，我希望模板记录对象 key、对象状态、URL 访问和端上渲染证据，以便快速判断问题发生在上传、存储、代理读取、缩略图派生还是小程序渲染阶段。

验收要点：

- [ ] key 检查能定位 object key 与业务资源的关系。
- [ ] object 检查能确认 MinIO 中对象存在性、MIME、大小和权限状态。
- [ ] URL 检查能记录 HTTP 状态、错误码和访问策略。
- [ ] miniapp render 检查能记录页面、组件和失败态表现。

## US-004 发布负责人使用模板做发布前媒体检查

作为发布负责人，我希望媒体变更能在发布前按统一模板补充证据，以便降低对象存储、域名、Nginx 或小程序配置导致的发布风险。

验收要点：

- [ ] 模板明确哪些媒体变更触发五联检查。
- [ ] 模板包含 Docker `:3000` 边界文件验收要求。
- [ ] 模板不记录真实密钥、内部路径、真实客户数据或 `.env` 内容。

## US-005 小程序开发使用模板确认端上渲染

作为小程序开发，我希望模板明确小程序媒体渲染验收要求，以便避免 Web 端可用但小程序端因组件、域名或资源策略限制失败。

验收要点：

- [ ] miniapp render 维度覆盖真机或等价预览环境。
- [ ] 图片、视频和缩略图场景可分别记录加载、播放、占位和失败态。
- [ ] 不涉及小程序时，模板要求记录 `n/a` 原因和影响判断。
