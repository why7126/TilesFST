# 用户故事

## US-001 运维按 Runbook 执行生产批量图片处理

作为实施 / 运维人员，我希望有一份标准 Runbook 指导我在生产环境执行批量图片转换、派生图生成、缩略图重建和对象 key 迁移，以便在不泄露密钥、不误连环境、不跳过备份的前提下完成媒体维护。

验收要点：

- Runbook 明确执行环境、Compose 文件、镜像版本、数据库类型和对象存储 provider。
- Runbook 明确只读审计、dry-run 和 apply 的区别。
- 写入型步骤必须要求备份、dry-run 通过和人工确认。
- 命令示例不得包含真实 `.env`、密钥、生产私有域名、Authorization header、Cookie、本机绝对路径或真实客户数据。

## US-002 发布负责人确认文档双投影

作为发布负责人，我希望批量图片处理 Runbook 同时有长期技术文档和版本使用文档快照投影，以便当前版本交付材料可追溯，后续版本也不会改写历史语义。

验收要点：

- 长期 Runbook 事实源归属 `docs/`。
- 发布或交付使用文档需要时，Runbook 投影到 `releases/vX.Y.Z/usage-docs/`。
- 版本快照必须通过 manifest 记录来源、版本、更新时间和适用范围。
- 旧版本内容性更正必须记录更正原因、范围和确认来源。

## US-003 开发和测试确认脚本能力边界

作为后端 / 媒体能力开发和测试人员，我希望 Runbook 明确图片转换脚本、派生图生成、缩略图重建和 key 迁移是否已有可执行能力，以便不会把未实现命令误写成生产可执行事实。

验收要点：

- Runbook 区分现有脚本、待改造脚本和待新增脚本。
- Runbook 说明每类脚本的输入范围、输出、幂等性、失败重试和日志位置。
- 未交付能力必须标记为后续治理范围或后续 OpenSpec Change，不得作为生产步骤直接执行。
- 对 API、数据库、Orval、Docker Compose、对象存储、Web、小程序和管理端影响给出矩阵。

## US-004 验收人员收集批处理证据

作为测试 / 验收人员，我希望 Runbook 提供验收证据模板，以便能基于 dry-run、apply、对象存储抽样、接口/数据库校验和端侧展示确认批量处理结果。

验收要点：

- 验收模板覆盖执行摘要、对象存储抽样、数据库或接口校验、端侧展示验证和失败对象清单。
- 缩略图和 `display` 派生图必须提供体积、加载或展示收益证据。
- 小程序、店主 Web、管理端缺少截图或日志时必须写 blocked 补证项，不得伪造通过。
- 失败对象、跳过原因、重试建议和回滚判断必须可追溯。

## US-005 产品负责人理解影响和回滚

作为产品 / 业务负责人，我希望 Runbook 说明批量图片处理影响哪些展示链路和数据资产，以便在生产执行前能判断是否允许执行、是否需要回滚或是否需要延期。

验收要点：

- Runbook 说明批处理任务对商品图、品牌 Logo、证书图片、Banner、详情预览和列表展示的影响。
- Runbook 明确对象 key 迁移、派生图重建和数据库回填的回滚边界。
- 删除对象或清理历史对象必须作为高风险动作单独确认。
- Runbook 收尾记录包含执行人、时间、命令参数、版本、证据路径和人工确认结论。
