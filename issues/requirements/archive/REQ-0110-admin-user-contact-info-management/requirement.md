# REQ-0110 用户管理页支持维护用户联系邮箱和手机号码

## 1. 需求背景

`REQ-0005-user-management` 已提供管理后台用户管理能力，支持后台管理员维护用户的用户名、头像、昵称、角色、状态与密码。当前用户列表响应和底层 `users` 表已存在 `email`、`phone` 字段，但管理端用户创建/编辑弹窗尚未形成联系邮箱和手机号码的维护闭环。

随着店主账号、后台运营账号和管理员账号数量增长，后台管理员需要在用户管理页直接补充和修正用户联系信息，便于线下沟通、账号归属识别和后续运营扩展。本需求将邮箱和手机号定位为 **联系信息**，不作为登录凭证、唯一身份或通知通道。

## 2. 目标用户

- **后台管理员**：在用户管理页创建或编辑用户时维护联系邮箱、手机号码。
- **后台运营**：无用户管理权限，本需求不扩大其可见或可操作范围。
- **店主/前台用户**：本需求不新增自助维护入口，仅影响管理员代维护能力。

## 3. 范围

### 3.1 本期包含

- 用户管理添加/编辑弹窗新增「联系邮箱」「手机号码」字段。
- 管理端创建用户、编辑用户接口支持保存、回填、清空联系邮箱和手机号码。
- 用户管理列表在「状态」列后新增「联系邮箱」「手机号码」两个独立列，避免管理员保存后无法确认。
- 关键词搜索支持匹配用户名、昵称、联系邮箱、手机号码。
- 邮箱和手机号均允许为空；不要求唯一。
- 手机号采用宽松格式校验，允许数字、空格、`+`、`-`，不绑定单一国家或地区格式。

### 3.2 本期不包含

- 不将邮箱或手机号作为登录账号。
- 不新增邮箱/短信验证码、通知、找回密码或订阅能力。
- 不要求邮箱或手机号唯一，不做跨用户冲突拦截。
- 不新增用户导入导出、批量修改或高级筛选。
- 不变更用户角色、状态、权限模型和超级管理员保护策略。
- 不新增数据库字段；若现有环境缺少字段，仅通过既有 migration/schema 机制保证兼容。

## 4. 功能要求

### FR-001 添加/编辑弹窗维护联系信息

- 用户管理页「添加用户」弹窗 MUST 新增「联系邮箱」「手机号码」字段。
- 用户管理页「编辑用户」弹窗 MUST 回填并允许修改「联系邮箱」「手机号码」字段。
- 字段推荐顺序：
  1. 用户名
  2. 头像
  3. 昵称
  4. 联系邮箱
  5. 手机号码
  6. 角色
- 两个联系字段 MUST 允许为空；管理员清空字段并保存后，后端应保存为空值。
- 编辑模式下用户名仍为只读；本需求不得放开用户名修改。

### FR-002 联系邮箱校验

- 联系邮箱为空时 MUST 允许保存。
- 联系邮箱非空时 MUST 进行邮箱格式校验。
- 邮箱前后空白 MUST 在保存前裁剪。
- 邮箱不要求唯一；不同用户可填写相同邮箱。
- 邮箱仅作为联系信息，MUST NOT 影响登录、权限、密码重置或账号状态判断。

### FR-003 手机号码校验

- 手机号码为空时 MUST 允许保存。
- 手机号码非空时 MUST 使用宽松格式校验：
  - 允许数字、空格、`+`、`-`。
  - 保存前裁剪前后空白。
  - 不绑定中国大陆或其他单一国家/地区号码格式。
- 手机号码不要求唯一；不同用户可填写相同手机号。
- 手机号码仅作为联系信息，MUST NOT 影响登录、权限、密码重置或账号状态判断。

### FR-004 创建与编辑接口

- `POST /api/v1/admin/users` MUST 接收 `email`、`phone` 可选字段，并在创建用户时写入。
- `PATCH /api/v1/admin/users/{id}` MUST 接收 `email`、`phone` 可选字段，并支持修改或清空。
- `GET /api/v1/admin/users` 与 `GET /api/v1/admin/users/{id}` MUST 返回用户当前 `email`、`phone`。
- 仅 `role=admin` 可调用管理端用户接口；employee、store_owner 权限边界保持不变。
- API 变更后 MUST 同步 OpenAPI 与 Orval 前端客户端。

### FR-005 列表展示与搜索

- 用户管理列表 MUST 在「状态」列后新增「联系邮箱」「手机号码」两个独立列。
- 用户管理列表表头顺序 MUST 为：用户、角色、状态、联系邮箱、手机号码、最后登录、创建时间、操作。
- 联系邮箱或手机号码为空时，列表对应单元格 MUST 显示 `-`。
- 创建时间 MUST 按 `yyyy-mm-dd hh:MM` 分钟级格式显示。
- 已维护联系信息的用户，管理员应能在列表或编辑回填中快速确认保存结果。
- 关键词搜索 MUST 匹配：
  - 用户名 `username`
  - 昵称 `display_name`
  - 联系邮箱 `email`
  - 手机号码 `phone`
- 搜索输入 placeholder 或帮助文案 SHOULD 从「搜索用户名/昵称」调整为能表达「用户名/昵称/邮箱/手机」的文案。

### FR-006 错误反馈

- 邮箱格式非法时 MUST 返回统一业务错误响应，并在前端表单内展示可理解提示。
- 手机号码包含不允许字符时 MUST 返回统一业务错误响应，并在前端表单内展示可理解提示。
- 已删除用户仍不可编辑；受保护账号仍不可编辑，既有保护策略不变。

## 5. UI / UE 约束

- 继承现有管理后台用户管理页视觉、布局和弹窗风格。
- 使用 Design System semantic token 与既有 `user-management.css` / 管理端表单样式，不引入裸 Hex。
- 新增字段在移动端和窄屏弹窗内不得溢出；标签、输入框和错误提示需保持单列可读。
- 用户新增/编辑弹窗标题区应紧凑展示，标题上方不得出现过大空隙。
- 用户新增/编辑弹窗整体应靠近视口顶部展示，不得因垂直居中在弹窗顶部留下过大空隙。
- 联系字段属于编辑信息，不应在页面顶部或指标卡中过度强调。

## 6. 数据与接口约束

- `users.email`、`users.phone` 作为联系信息字段保存。
- SQLite 与 MySQL schema/migration 如已包含字段，不得重复新增；如兼容历史环境，需要通过现有 migration 检测缺失列并补齐。
- Pydantic Schema 需明确 `email`、`phone` 的可选性与校验策略。
- 前端类型以 Orval 生成结果为准，不手写绕过 API 类型。

## 7. 测试要求

- 后端集成测试覆盖：
  - 创建用户保存邮箱和手机号。
  - 编辑用户修改、清空邮箱和手机号。
  - 邮箱非法、手机号非法返回业务错误。
  - 关键词搜索可命中邮箱和手机号。
  - 非管理员权限仍被拒绝。
- 前端组件或页面测试覆盖：
  - 添加/编辑弹窗字段展示、回填和提交 payload。
  - 清空邮箱/手机号后提交空值。
  - 列表展示或搜索 placeholder 更新。
- API 生成物测试或类型检查覆盖 Orval 更新后的调用类型。
