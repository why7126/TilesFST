# 一句话

日志审计页面的操作者筛选从难以识别的 User ID 改为用户名称，并支持单选下拉和下拉内模糊搜索。

# 原始描述

日志审计页面，操作者使用User ID很难使用，改成用户名称，支持单选下拉，支持下拉时模糊搜索

# 背景与关联

- 使用痛点：审计人员或管理员在日志审计页面按操作者筛选时，User ID 不具备可读性，难以快速判断具体人员。
- 业务价值：使用用户名称作为主筛选入口，降低审计查询成本，提高操作日志排查效率。
- 交互价值：单选下拉可避免误输入，模糊搜索可在用户数量较多时快速定位目标操作者。

# 影响范围

- 管理端：日志审计页面操作者筛选控件、筛选条件展示、查询参数组装。
- 后端 API：如当前日志查询接口仅接受 User ID，需要评估是否新增用户名称搜索接口、操作者候选列表接口，或前端先通过用户列表查询映射 ID。
- 权限边界：操作者候选列表必须遵守管理端权限，不应暴露超出当前管理员可见范围的用户信息。
- 审计语义：日志记录本身仍应保留稳定的操作者 ID；页面展示和筛选交互可显示用户名称，并在必要时携带 ID 作为实际过滤值。

# 初步需求要点

- 日志审计页面操作者筛选项展示用户名称，而不是直接要求用户输入或选择 User ID。
- 筛选控件为单选下拉，一次只能选择一个操作者；允许清空筛选恢复全部日志。
- 下拉展开后支持按用户名称模糊搜索；如本期有账号、手机号、用户名等字段，也可作为辅助匹配字段，但展示主文案应优先为用户名称。
- 选择用户名称后，日志查询结果应按对应操作者准确过滤；同名用户需要有可区分的辅助信息，避免误选。
- 空态、加载态、搜索无结果、接口失败态需要有明确反馈，并复用管理端 Design System 组件与语义 token。
- 已选筛选条件、URL 查询参数或页面状态应避免只暴露难读 ID；如必须保留 ID，应在界面上同步显示用户名称。

# 待澄清

- [ ] 当前日志审计页面的操作者字段来源于哪个 API，是否已有用户候选列表接口可复用。
- [ ] 用户名称字段应使用真实姓名、昵称、用户名，还是多字段组合展示。
- [ ] 模糊搜索由前端本地过滤还是后端远程搜索，用户量超过多少时需要分页/防抖。
- [ ] 是否需要在日志列表行中同步把操作者列从 User ID 展示为用户名称。

# 建议验收要点

- [ ] 进入日志审计页面，操作者筛选控件显示为单选下拉，不再要求直接使用 User ID。
- [ ] 下拉列表展示用户名称，并能通过输入关键字进行模糊搜索。
- [ ] 选择某个用户名称后，日志列表仅展示该操作者相关记录；清空后恢复全部记录。
- [ ] 同名用户在下拉中能通过辅助信息区分，避免选错。
- [ ] 用户候选列表加载失败、无匹配结果、权限不足时，页面有清晰反馈且不影响其他筛选条件使用。
