# REQ-0070 日志审计页面操作者名称筛选

## 1. 需求背景

管理端日志审计页面用于系统管理员查询 API 请求日志、产品行为事件和审计操作。当前日志列表已经在“操作者”列展示人类可读的操作者信息，例如用户名称、角色或 anonymous；但筛选区仍要求用户输入 `User ID`，这对审计查询并不友好。

在真实排查场景中，系统管理员通常知道的是“谁操作了这件事”，而不是用户表里的 UUID 或内部 ID。直接使用 User ID 会带来以下问题：

- 需要先到用户管理或数据库中查找 ID，审计查询链路变长；
- 对同一问题的沟通往往使用姓名、昵称或账号，User ID 难以人工核对；
- 输入框无法避免拼写错误，筛选无结果时也难以判断是没有日志还是 ID 输入错误；
- 用户数量增长后，靠记忆或复制 User ID 筛选会进一步降低排查效率。

因此，本需求要求将日志审计页面的操作者筛选从 User ID 输入优化为“按用户名称搜索并单选”的下拉控件。底层审计日志仍保留稳定的 `actor_user_id` 作为过滤条件，界面层负责提供用户名称、账号等可读信息。

## 2. 目标用户

| 用户 | 诉求 |
|---|---|
| 系统管理员 | 按用户名称快速筛选日志，定位某个操作者的请求、行为事件和审计操作。 |
| 企业内部运营人员 | 在协助排查时能基于姓名或账号描述问题，不需要理解内部 User ID。 |
| 开发 / 运维人员 | 保留稳定的 `actor_user_id` 查询语义，避免按名称过滤导致同名、改名、历史日志不稳定。 |
| 安全 / 审计负责人 | 审计筛选更易用，同时不降低操作者身份追溯的准确性。 |

## 3. 需求目标

- 日志审计页面操作者筛选控件展示为单选可搜索下拉。
- 下拉候选项只展示账号与用户名称两行，账号用于同名区分。
- 用户在下拉中按名称或账号模糊搜索操作者。
- 选择操作者后，日志查询仍使用稳定的 `actor_user_id` 过滤。
- 已选条件在界面上显示用户名称，不再要求用户直接输入或识别 User ID。
- 控件必须支持清空、加载、无匹配结果和接口失败等状态。
- 实现优先复用现有用户列表 API 与前端 SearchableSelect 能力，避免新增不必要接口。

### 4.1 本期包含

| 范围 | 说明 |
|---|---|
| 操作者筛选控件替换 | 将日志审计页面现有 User ID 输入框替换为单选可搜索下拉。 |
| 用户候选搜索 | 下拉展开后支持按用户名称、账号等字段模糊搜索用户候选。 |
| 筛选语义保持稳定 | 选择候选项后，日志列表查询仍传递对应用户的 `id` 作为 `actor_user_id`。 |

### 4.2 本期不包含

| 不包含 | 说明 |
|---|---|
| 改写审计日志事实源 | 不改变 `request_logs`、`usage_events`、`audit_logs` 中操作者 ID 的事实记录语义。 |

| 用户管理能力扩展 | 不新增用户创建、编辑、角色管理或用户详情能力。 |
| 复杂多选筛选 | 操作者筛选为单选，不支持一次选择多个操作者。 |
| 独立审计操作者管理页 | 不新增独立页面，只优化日志审计页面筛选区。 |
| 非管理端入口 | 小程序、店主 Web 展示端不展示该筛选能力。 |

## 5. 核心概念

### 5.1 展示值与过滤值

本需求区分“用户看到的值”和“系统查询的值”：

```text
展示值: display_name || username
候选展示: 第一行 username，第二行 display_name || username
过滤值: user.id -> actor_user_id
```

这样既能让管理员按名称选择操作者，也能让后端继续按稳定 ID 精确过滤日志。

### 5.2 用户候选项

用户候选项用于下拉选择，不等同于完整用户管理列表。候选项必须至少包含：

| 字段 | 用途 |
|---|---|
| `id` | 作为日志查询的 `actor_user_id`。 |
| `display_name` | 候选第二行用户名称；为空时回退到 `username`。 |
| `username` | 候选第一行账号，用于搜索和同名区分。 |
| `role` | 可由复用用户列表 API 返回，但下拉候选不展示。 |
| `status` | 可由复用用户列表 API 返回，但下拉候选不展示。 |

如果复用现有用户列表 API，前端可从 `UserAdminItem` 映射为下拉候选项。

## 6. 功能要求

### FR-001 操作者筛选控件

- 日志审计页面 MUST 将操作者筛选从普通输入框改为单选可搜索下拉。
- 下拉控件 MUST 支持键入关键字后搜索候选用户。
- 控件收起且已选择用户时，MUST 展示用户名称；名称为空时展示账号。
- 控件 MUST 支持清空已选操作者，并触发日志列表按全部操作者查询。
- 页面“重置”操作 MUST 清空操作者筛选，与其他筛选项一起恢复默认状态。

### FR-002 用户候选搜索

- 系统 MUST 支持按用户名称模糊搜索操作者候选。
- 系统 SHOULD 同时支持按账号模糊搜索，以便名称为空或管理员只知道账号时仍可定位。
- 用户候选搜索 SHOULD 使用防抖，避免每次键入都立即请求接口。
- 用户候选搜索 MUST 有数量上限或分页策略，避免一次性加载过多用户。
- 当关键字为空且下拉展开时，系统 MAY 展示最近创建、最近活跃或默认分页的用户列表；具体排序可沿用用户列表 API。

### FR-003 候选项展示与同名区分

- 候选项 MUST 只展示两行：第一行账号 `username`，第二行用户名称 `display_name || username`。
- 候选项 MUST NOT 展示角色、状态、密码、Token、内部绝对路径、敏感备注或其他非必要信息。
- 当多个用户展示名称相同，系统 MUST 通过账号行提供可区分信息，避免管理员误选。
- 已删除用户是否出现在候选列表由实现阶段确定，但必须保证历史日志中已存在的操作者仍可被理解；如候选列表排除已删除用户，应在 PRD/设计中说明历史日志筛选限制。
- 候选项不得展示密码、Token、内部绝对路径、敏感备注或其他非必要信息。

### FR-004 日志查询行为

- 用户选择候选项后，日志列表查询 MUST 使用该候选项的 `id` 填充 `actor_user_id`。
- 日志列表接口现有 `actor_user_id` 查询语义 SHOULD 保持不变。
- 系统 MUST 避免把显示名称直接传给日志查询接口作为 `actor_user_id`。
- 切换操作者筛选后，日志列表 MUST 回到第一页并重新查询。
- 其他筛选条件，如日志类型、时间范围、状态、Task Trace ID、路径 / Request ID，必须与操作者筛选组合生效。
- 时间范围 MUST 固定为最近5分钟、最近10分钟、最近30分钟、最近1小时、最近3小时、最近6小时、最近12小时、最近1天、最近2天、最近3天和最近7天，且 MUST NOT 提供全部时间。

### FR-005 状态与异常反馈

- 候选搜索加载中时，控件 SHOULD 显示加载状态或禁用重复选择反馈。
- 搜索无匹配结果时，控件 MUST 显示“无匹配结果”或等价提示。
- 候选接口失败时，页面 MUST 提供失败提示，并允许用户继续使用其他日志筛选条件。
- 日志列表查询失败与用户候选查询失败 MUST 有区分，避免管理员误判日志系统不可用。
- 清空操作者筛选后，候选加载失败不应阻断日志列表按全部操作者查询。

### FR-006 权限与安全

- 操作者候选列表 MUST 复用管理端鉴权，仅系统管理员可访问日志审计页面及其候选数据。
- 前端不得绕过后端权限控制直接访问数据库或未授权用户数据。
- 用户候选数据 MUST 仅返回筛选所需字段或复用已授权的用户列表字段。
- 后端日志查询仍必须按当前用户权限校验，不得因为前端传入某个 `actor_user_id` 而泄露无权查看的日志。
- URL、埋点或错误提示中不得暴露敏感用户字段；如保留 `actor_user_id` 作为查询状态，应确保仅在管理端授权上下文中使用。

### FR-007 API 与契约

- 若复用现有用户列表 API，本需求可不新增后端接口，但实现时 MUST 确认该 API 支持 `keyword`、`page_size` 和系统管理员鉴权。
- 若现有用户列表 API 无法满足候选搜索性能或权限需求，MAY 新增轻量用户候选接口。
- 如新增或修改 API 字段，MUST 同步 OpenAPI、Orval、前端类型和相关 API 文档。
- 日志列表 API 的 `actor_user_id` 参数 SHOULD 保持兼容，避免影响现有测试和调用方。
- 错误响应必须使用统一 `ApiResponse` 与既有错误码体系。

### FR-008 测试与验收支撑

- 前端测试 MUST 覆盖：下拉渲染、关键字搜索、选择用户、清空筛选、重置筛选、日志查询参数为 `actor_user_id`。
- 前端测试 SHOULD 覆盖：无匹配结果、候选加载失败、同名用户账号区分、时间范围固定窗口和列表操作者账号单行展示。
- 如果改动后端 API，后端测试 MUST 覆盖候选搜索权限、keyword 查询、分页上限和返回字段。
- 如果改动 OpenAPI/Orval，必须运行对应生成与类型检查，并避免手改生成物。

## 7. UI 约束

- 筛选区继续复用日志审计页面现有管理端列表页结构，不新增营销式区域。
- 操作者控件应与其他筛选项高度、间距、标签样式一致。
- 优先复用现有 `SearchableSelect` 或同等 Design System 组件，避免重复实现独立控件。
- 下拉面板宽度应与输入区域匹配，移动端不得溢出屏幕。
- 候选项账号行和用户名称行应层级清晰，长账号或名称需要截断并保留可识别信息。
- 控件状态色、边框、文字颜色必须使用 Design System semantic token，不得新增裸 Hex。
- 加载、空态、错误态文案应简短明确，不遮挡其他筛选控件。
