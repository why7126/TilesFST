# REQ-0087 管理端 SKU 列表排序优化

## 1. 需求背景

管理端 SKU 列表用于后台运营集中维护商品资料、图片素材、视频素材与上下架状态。当前运营在处理 SKU 时，通常需要优先关注尚未上架的商品，以便完成内容补齐、素材检查和发布准备；对于已经上架的商品，则更关注最近发布的商品，便于巡检新品展示和确认发布结果。

现有列表如果仅按统一时间字段排序，容易把未上架 SKU 与已上架 SKU 混在一起，运营需要额外筛选或翻页才能找到待处理内容。因此，本需求要求优化管理端 SKU 列表默认排序：先按是否上架分组，未上架 SKU 优先；未上架分组内按创建时间降序；已上架分组内按发布时间降序。

## 2. 目标用户

| 用户 | 核心诉求 |
|---|---|
| 后台运营 | 优先看到未上架 SKU，快速处理待发布商品。 |
| 后台管理员 | 在同一个列表中稳定查看未上架与已上架商品的先后顺序。 |
| 产品 / 业务负责人 | 明确 SKU 列表默认排序规则，减少运营侧对排序逻辑的理解成本。 |
| 开发 / 测试人员 | 明确排序字段、状态分组、空值兜底和分页一致性，降低实现与验收歧义。 |

## 3. 需求目标

- SKU 列表默认先展示未上架 SKU，再展示已上架 SKU。
- 未上架 SKU 分组内按创建时间降序排列。
- 已上架 SKU 分组内按发布时间降序排列。
- 排序规则在搜索、筛选、分页后保持稳定，避免跨页顺序错乱。
- 排序逻辑不得改变 SKU 上下架状态、发布时间、创建时间和更新时间的字段语义。
- 如排序需要后端支持，必须同步接口契约、OpenAPI、Orval 与测试。

## 4. 范围

### 4.1 本期包含

| 范围 | 说明 |
|---|---|
| 默认排序策略 | 管理端 SKU 列表默认按上架状态与对应时间字段排序。 |
| 未上架优先 | 所有未上架 SKU 排在已上架 SKU 之前。 |
| 未上架组内排序 | 未上架 SKU 按创建时间降序排列，最新创建的排在前面。 |
| 已上架组内排序 | 已上架 SKU 按发布时间降序排列，最新发布的排在前面。 |
| 分页一致性 | 排序必须在完整结果集层面生效，再进行分页。 |
| 空值兜底 | 创建时间或发布时间缺失时必须有稳定兜底顺序，不得导致列表报错。 |
| 回归测试 | 覆盖默认排序、分组排序、空值场景和筛选分页后的稳定性。 |

### 4.2 本期不包含

| 不包含 | 说明 |
|---|---|
| 新增显式排序控件 | 不新增“按上架/创建/发布时间排序”的 UI 控件，除非实现阶段确认已有排序控件需要同步默认值。 |
| 新增筛选条件 | 不新增按创建时间、发布时间或上架状态之外的新筛选项。 |
| 发布流程改造 | 不调整 SKU 发布、下架、重新上架或发布时间生成流程。 |
| 历史数据清洗 | 不批量修复历史 SKU 的发布时间或创建时间；历史异常数据按兜底规则处理。 |
| 店主 Web / 小程序排序 | 不调整公开端或小程序商品列表排序。 |
| 导出排序规则 | 不调整 SKU 导出文件的排序，除非导出复用同一列表接口且后续 Change 明确纳入。 |

## 5. 核心概念

### 5.1 未上架 SKU

“未上架 SKU”指当前未处于已上架发布态的 SKU。实现阶段需结合现有状态枚举确认覆盖范围，通常包括草稿、待完善、已下架、已停用等非上架状态。

若状态枚举存在业务差异，OpenSpec Change 中必须明确哪些状态属于未上架分组，避免前后端各自判断。

### 5.2 已上架 SKU

“已上架 SKU”指当前处于已上架发布态、可被业务展示或进入公开展示链路的 SKU。已上架 SKU 的组内排序使用发布时间，不使用更新时间或创建时间替代。

### 5.3 创建时间

创建时间表示 SKU 记录首次创建的时间。未上架 SKU 使用创建时间降序，是为了让最新录入、最需要处理的待发布内容优先出现。

### 5.4 发布时间

发布时间表示 SKU 最近进入已上架发布态的时间，字段语义需与 `REQ-0079-admin-sku-list-published-at` 保持一致。已上架 SKU 使用发布时间降序，是为了让最新发布的商品优先出现。

## 6. 功能要求

### FR-001 默认排序分组

- 管理端 SKU 列表默认排序 MUST 先按是否上架分组。
- 未上架 SKU MUST 排在已上架 SKU 之前。
- 上架状态判断 MUST 使用系统现有 SKU 状态字段或后端统一派生字段。
- 前端不得仅通过显示文案推断上架状态。
- 若存在未知状态，系统 MUST 按明确兜底规则归入未上架或置于末尾，并在后续实现文档中说明。

### FR-002 未上架 SKU 组内排序

- 未上架 SKU 分组内 MUST 按创建时间降序排列。
- 创建时间较新的 SKU MUST 排在创建时间较旧的 SKU 前面。
- 创建时间相同的 SKU MUST 使用稳定的次级排序字段，例如 SKU ID 降序或更新时间降序。
- 创建时间为空、缺失或不可解析时，MUST 使用稳定兜底顺序，不得导致列表接口或页面渲染失败。

### FR-003 已上架 SKU 组内排序

- 已上架 SKU 分组内 MUST 按发布时间降序排列。
- 发布时间较新的 SKU MUST 排在发布时间较旧的 SKU 前面。
- 发布时间相同的 SKU MUST 使用稳定的次级排序字段，例如 SKU ID 降序或更新时间降序。
- 已上架 SKU 发布时间为空时，MUST 明确兜底策略，不得使用随机顺序。
- 不得用更新时间替代发布时间作为已上架 SKU 的主排序字段。

### FR-004 搜索、筛选与分页一致性

- 关键词搜索后的结果 MUST 继续应用本需求的默认排序策略。
- 品牌、类目、状态、素材完整度等筛选后的结果 MUST 继续应用本需求的默认排序策略。
- 分页 MUST 基于排序后的完整结果集切分，不能只在当前页内排序。
- 翻页、调整每页条数、刷新列表后，排序结果 MUST 保持稳定。
- 新建、编辑、上架或下架 SKU 后刷新列表时，SKU 应按最新状态和对应时间字段进入正确位置。

### FR-005 API 与实现边界

- 若管理端 SKU 列表由后端分页接口提供，排序 SHOULD 在后端完成，确保分页前全量有序。
- 若当前实现为前端获取完整数据后分页，前端可在本地排序，但必须保证分页前排序。
- 如果需要新增排序参数、响应字段或派生字段，MUST 同步 Pydantic Schema、OpenAPI、Orval、接口文档和相关测试。
- 接口鉴权、分页结构、错误码和既有筛选参数不得因排序优化发生不兼容变化。
- 前端不得手写与后端重复的接口类型；API 类型仍应以 Orval 生成物为准。

### FR-006 UI 与交互表现

- 本需求不新增页面说明、提示卡片或额外排序控件。
- SKU 列表视觉结构、列顺序、筛选区、分页区和操作列保持现有样式。
- 如已有表格列头排序状态，本需求只影响默认排序，不要求新增可点击排序能力。
- 列表加载中、空数据、接口失败等状态保持现有展示方式。
- 排序变化不得造成行高度、列宽、状态标签或操作按钮布局抖动。

### FR-007 权限与安全

- 排序能力仅在管理端授权 SKU 列表中生效。
- 不得绕过管理端鉴权获取未上架 SKU 或发布时间数据。
- 不得在 URL、日志或错误提示中暴露额外敏感信息。
- 排序字段应使用参数化查询、ORM 排序或等价安全机制，不得拼接不可信 SQL。

### FR-008 测试与验收支撑

- 后端或前端测试 MUST 覆盖未上架 SKU 优先于已上架 SKU。
- 测试 MUST 覆盖未上架 SKU 按创建时间降序。
- 测试 MUST 覆盖已上架 SKU 按发布时间降序。
- 测试 MUST 覆盖同一状态分组内时间相同或时间为空的稳定排序。
- 测试 MUST 覆盖搜索或筛选后排序仍然正确。
- 若排序由后端分页接口实现，测试 MUST 覆盖分页前排序而非页内排序。

## 7. UI 约束

- 页面继续复用管理端 SKU 列表现有布局，不新增营销式或说明型区域。
- 表格、筛选区、分页区、状态标签和操作按钮保持现有 Design System 语义 token。
- 不新增裸 Hex 颜色，不改变管理端暗色旗舰风。
- 若已有表头排序图标或状态，本需求不强制新增图标；如实现需要展示默认排序状态，必须使用现有表格交互模式。
- 排序后的列表项不得出现文本重叠、时间字段溢出或操作列被压缩不可用。

## 8. 数据与接口影响

| 范围 | 影响 |
|---|---|
| SQLite/MySQL | 可能需要确认 SKU 状态、创建时间、发布时间字段是否支持排序；通常不要求新增表结构。 |
| Pydantic Schema | 若需要返回发布时间、排序字段或派生上架状态，需同步管理端 SKU 列表响应 Schema。 |
| OpenAPI/Orval | 如接口响应或排序参数变化，必须同步 OpenAPI 和 Orval。 |
| 管理端 Web | SKU 列表默认排序逻辑调整，筛选分页后保持一致。 |
| 小程序 | 本期不涉及。 |
| 店主 Web | 本期不涉及。 |
| 测试 | 需覆盖分组排序、时间字段排序、空值兜底、筛选分页稳定性。 |
