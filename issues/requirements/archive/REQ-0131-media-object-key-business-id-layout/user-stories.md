# 用户故事

## US-001 管理端上传媒体自动归属业务对象

作为企业管理端用户，我希望上传头像、品牌 Logo、Banner、SKU 图片、SKU 视频和品牌证书时，系统自动把媒体归属到对应业务对象目录中，以便后续编辑、展示和排障时能稳定追溯媒体来源。

验收要点：

- 上传前业务对象已存在时，新媒体直接写入业务对象 id 目录。
- 上传前业务对象不存在时，新媒体先写入对应 `pending` 目录。
- 保存业务对象成功后，pending 媒体会 formalize 到业务对象 id 目录。
- 保存失败时，业务记录不得引用不存在或未完成归属的对象。

## US-002 小程序和店主端继续稳定展示旧媒体

作为小程序或店主端访问者，我希望系统升级对象 Key 策略后，旧商品图、品牌 Logo、证书图片和证书 PDF 仍能正常展示或预览，以免升级后出现空白图、404 或文件打不开。

验收要点：

- 旧数据库引用中的完整 key 仍可通过受控 `/media/{object_key}` 或等价 URL 读取。
- 新旧 key 并存期间，客户端只消费后端返回 URL，不自行拼接业务 id 目录。
- 缩略图或展示图缺失时，页面按已定义 fallback 或占位策略处理。
- 小程序媒体位需提供 render 或 Network evidence。

## US-003 运维可安全迁移历史对象

作为实施或运维人员，我希望历史媒体迁移有 dry-run、apply、二次审计、幂等和回滚边界，以便在生产环境可控地把旧 key 迁移到业务对象 id 目录。

验收要点：

- dry-run 不写数据库或对象存储，只输出脱敏统计、失败分类和风险摘要。
- apply 执行前必须确认数据库与对象存储备份。
- apply 后可二次审计数据库引用、对象存在性、URL 可读性和端侧展示。
- 旧对象删除必须作为单独高风险动作确认。

## US-004 开发和测试有统一规范矩阵

作为后端、前端和测试负责人，我希望文档中有完整对象 Key 策略矩阵，明确每类媒体的业务 id、pending 目录、正式化时机、派生图位置、迁移和验收要求。

验收要点：

- 矩阵覆盖头像、品牌 Logo、Banner 图片、SKU 图片、SKU 视频、品牌证书图片和 PDF/文档。
- 文档明确 API、DB、Orval、Task Trace、请求日志、Web、小程序和 Docker 验证影响。
- 新增媒体类型必须先补矩阵和验收口径，再实现上传或展示逻辑。
- 规范禁止客户端拼接对象存储 endpoint、bucket、raw URL 或最终 object key。

## US-005 发布负责人能判断升级风险

作为发布负责人，我希望本需求的交付材料能说明旧 key 兼容、迁移窗口、回滚责任、对象清理策略和发布验收结果，以便判断是否可以进入生产升级。

验收要点：

- 发布材料说明只改新上传、迁移存量对象或清理旧对象的具体范围。
- 版本升级计划包含 DB 备份、对象存储 bucket/prefix 备份和回滚边界。
- 验收报告覆盖 key、object、URL、render/Network、耗时或 trace span。
- 若生产迁移未执行，必须说明旧 key 兼容仍生效。
