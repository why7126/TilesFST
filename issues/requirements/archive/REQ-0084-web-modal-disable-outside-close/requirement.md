# REQ-0084 Web 端所有弹窗禁用点击空白区域自动关闭

## 1. 需求背景

Web 端管理端与展示端中存在多类弹窗交互，包括表单编辑、详情查看、确认操作、图片预览、上传配置等。当前部分弹窗支持点击遮罩或弹窗外空白区域自动关闭，用户在维护 SKU、品牌、类目、证书、Banner 等资料时，如果误触空白区域，可能导致当前编辑流程中断、未保存内容丢失或二次确认操作被意外取消。

本需求要求 Web 端电脑端的标准弹窗统一取消“点击空白区域自动关闭”行为，改为必须通过明确关闭入口或完成操作后关闭，以降低误触风险并统一弹窗交互策略。

本需求仅定义需求草案范围；具体覆盖组件、例外清单、Esc 键策略、未保存改动二次确认策略在后续 `/req-complete` 阶段进一步补齐。

## 2. 目标用户

| 用户 | 诉求 |
|---|---|
| 后台管理员 / 内部员工 | 在管理后台编辑商品、品牌、类目、证书、Banner 等资料时，避免误点弹窗外区域导致编辑流程中断。 |
| 运营与商品维护人员 | 在长表单、上传、选择器等复杂弹窗内操作时，保持输入内容和操作上下文稳定。 |
| 店主 Web 展示端访问者 | 在查看详情、图片预览或确认类弹窗时，获得一致且可预期的关闭方式。 |

## 3. 范围

### 3.1 本期包含

| 范围 | 说明 |
|---|---|
| Web 端标准弹窗策略调整 | 管理端和 Web 展示端中使用标准 Dialog / Modal 的弹窗点击外部空白区域时不自动关闭。 |
| 明确关闭入口保留 | 弹窗仍需保留取消按钮、关闭图标、确认完成或保存成功后的关闭路径。 |
| 表单弹窗覆盖 | SKU、品牌、类目、证书、Banner 等资料维护相关弹窗应遵循统一策略。 |
| 确认与详情弹窗覆盖 | 删除确认、状态切换确认、详情查看等标准弹窗应遵循统一策略，除非后续评审明确例外。 |
| 组件级默认配置 | 如项目存在统一 Dialog / Modal 封装，应优先在组件默认配置层统一约束，减少页面级重复配置。 |
| 回归检查 | 确认禁用外部点击关闭后，弹窗内滚动、上传、选择、保存、取消和关闭图标仍可正常使用。 |

### 3.2 本期不包含

| 不包含 | 说明 |
|---|---|
| 小程序弹窗策略 | 本需求只覆盖 Web 端电脑端，不调整微信小程序原生弹窗、底部弹层或页面浮层。 |
| 非弹窗浮层统一治理 | Popover、Dropdown、Tooltip、Select 下拉层、日期选择器等轻量浮层是否纳入需在后续阶段确认，本草案不默认纳入。 |
| 未保存改动二次确认 | 点击取消按钮或关闭图标时是否触发二次确认，不在本草案直接定义，后续需作为独立规则明确。 |
| 弹窗视觉重设计 | 不调整弹窗尺寸、标题样式、按钮布局、遮罩颜色、动效或 Design System 视觉风格。 |
| 业务流程重构 | 不改变保存、删除、上传、审批、上下架等业务动作本身的权限、接口和状态流转。 |

## 4. 功能要求

### FR-001 禁用点击外部空白区域关闭

- Web 端标准 Dialog / Modal 类弹窗 MUST 禁用点击遮罩或弹窗外空白区域自动关闭。
- 用户在弹窗外部点击时，弹窗 MUST 保持打开，弹窗内已输入或已选择内容不得因此丢失。
- 该策略 SHOULD 作为统一组件默认行为实现；如存在无法复用统一组件的历史弹窗，后续实现需逐一补齐。
- 页面不得通过局部配置重新开启外部点击关闭，除非需求评审明确列为例外。

### FR-002 保留明确关闭路径

- 每个可关闭弹窗 MUST 至少保留一个明确关闭入口，例如取消按钮、关闭图标、返回按钮或业务完成后的自动关闭。
- 表单类弹窗保存成功后 SHOULD 沿用现有关闭逻辑；保存失败时 MUST 保持弹窗打开并展示错误反馈。
- 确认类弹窗的取消、确认按钮行为 MUST 保持明确，不得因为禁用外部点击关闭导致用户无法退出。
- 详情类或预览类弹窗如没有底部按钮，MUST 保留关闭图标或等价可见关闭入口。

### FR-003 覆盖管理端高风险编辑弹窗

- 管理端 SKU 维护相关弹窗 MUST 禁用点击外部空白区域关闭。
- 管理端品牌、类目、证书、Banner 等资料维护弹窗 MUST 禁用点击外部空白区域关闭。
- 上传图片、上传证书、上传视频或选择素材等涉及输入上下文的弹窗 MUST 禁用点击外部空白区域关闭。
- 批量操作、删除确认、上下架确认等确认弹窗 SHOULD 遵循同一关闭策略，避免误触导致确认流程中断。

### FR-004 覆盖 Web 展示端标准弹窗

- Web 展示端商品详情、品牌详情、图片预览、联系或咨询相关标准弹窗如存在，MUST 禁用点击外部空白区域关闭。
- Web 展示端弹窗关闭入口 MUST 对鼠标用户可见、可点击，并满足当前前端组件的可访问性基础要求。
- 禁用外部点击关闭不得影响弹窗内图片切换、滚动、表单输入或链接点击。

### FR-005 Esc 键与轻量浮层待确认

- Esc 键是否关闭弹窗为待确认项，后续 `/req-complete` 阶段需明确统一策略。
- Popover、Dropdown、Tooltip、Select 下拉层、日期选择器等轻量浮层是否纳入为待确认项，后续需按组件类型逐项界定。
- 若后续评审决定部分组件保留点击外部关闭，必须列出例外原因、适用组件和用户可感知影响。

### FR-006 组件与测试同步

- 如 Web 端存在统一 Dialog / Modal 封装，后续实现 SHOULD 优先修改统一封装默认配置。
- 如部分弹窗直接使用第三方组件或页面局部配置，后续实现 MUST 检查并同步对应关闭策略。
- 前端测试 SHOULD 覆盖至少一个表单弹窗和一个确认弹窗：点击弹窗外部区域后弹窗仍保持打开。
- 回归测试 SHOULD 覆盖明确关闭入口仍可关闭弹窗，保存成功后弹窗关闭，保存失败后弹窗保持打开。

## 5. UI / UE 约束

- 弹窗视觉风格、尺寸、按钮层级和暗色旗舰风 Design System 保持不变。
- 不新增说明性大段文案提示“点击外部不可关闭”；用户应通过明确关闭入口自然完成操作。
- 关闭图标、取消按钮或返回入口必须可见、语义明确，避免禁用外部点击后形成无出口弹窗。
- 禁用外部点击关闭不得引起弹窗位置跳动、遮罩层穿透、页面滚动异常或焦点丢失。
- 管理端弹窗实现必须继续使用 semantic token 和既有组件封装，不引入裸 Hex 或独立视觉体系。

## 7. 风险与待确认

| 风险 / 待确认 | 说明 |
|---|---|
| 覆盖范围边界 | “所有弹窗”需确认是否只包含 Dialog / Modal，还是扩展到 Popover、Dropdown、Tooltip、Select 等轻量浮层。 |
| Esc 键策略 | 需确认是否仅禁用鼠标点击外部关闭，还是同时禁用 Esc 键关闭。 |
| 历史弹窗差异 | 旧页面可能未复用统一弹窗组件，后续实现需盘点避免遗漏。 |
| 无明确关闭入口 | 少量详情或预览弹窗可能依赖遮罩关闭，禁用前需补齐关闭图标或按钮。 |
| 未保存改动保护 | 若用户主动点击取消或关闭图标，是否需要二次确认仍需单独明确。 |
