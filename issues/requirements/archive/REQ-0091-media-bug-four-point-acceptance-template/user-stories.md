# 用户故事

## US-001 产品负责人确认媒体 BUG 修复闭环

作为产品负责人，我希望媒体类 BUG 修复后能按统一模板检查 `key`、`object`、`URL`、`render` 四个维度，以便确认修复覆盖原始问题和用户可见影响。

验收要点：

- [ ] 能从验收记录中看到原 BUG 编号、影响范围、复现入口和修复后对照结论。
- [ ] 四个维度均有 `pass`、`fail`、`n/a` 或 `blocked` 状态。
- [ ] `n/a` 和 `blocked` 必须写明原因，不能空置。

## US-002 测试人员执行媒体缺陷回归

作为测试人员，我希望每个媒体类 BUG 都能按四联模板记录可复现入口、对象证据和端侧展示结果，以便减少漏验和返工。

验收要点：

- [ ] 模板能记录媒体类型、业务资源、对象 key、URL、渲染页面和截图/日志证据。
- [ ] 失败项能直接支撑原 BUG 返修或后续 `/bug-capture`。
- [ ] 对微信小程序相关 BUG，模板要求补充 DevTools、真机或体验版 evidence，或明确不可用原因。

## US-003 后端开发确认对象存储修复边界

作为后端 / 平台开发，我希望模板明确 key、object、URL 的验收标准，以便确认修复没有绕过 media 模块、MinIO 单桶策略和后端鉴权边界。

验收要点：

- [ ] `key` 检查要求对象 key 与业务记录可追溯，禁止原始文件名、本机路径和临时路径。
- [ ] `object` 检查要求对象存在、类型/大小/权限符合规则，且不泄露 MinIO 凭证或内部路径。
- [ ] `URL` 检查要求前端不直连未授权对象存储，失败时记录 HTTP 状态、业务错误码和排查线索。

## US-004 前端与小程序开发确认渲染结果

作为前端 / 小程序开发，我希望模板明确各端 render 验收范围，以便确认媒体在管理端、店主 Web 和微信小程序端正确展示，并有可诊断失败态。

验收要点：

- [ ] Web 管理端覆盖上传后预览、列表缩略展示、详情或编辑弹窗展示。
- [ ] 店主 Web 展示端覆盖公开页面、商品卡片、详情页或媒体预览入口。
- [ ] 小程序端覆盖合法域名、图片/视频组件限制、占位、失败态和不依赖 Web 浏览器专属 API。

## US-005 发布负责人检查发布风险

作为发布负责人，我希望媒体类 BUG 发布前有固定四联证据，以便确认对象存储、域名、签名 URL、小程序资源访问或性能优化没有回归。

验收要点：

- [ ] 发布前可按模板识别是否需要 Docker `:3000` 上传边界文件验证。
- [ ] 涉及媒体依赖、缩略图或对象处理脚本时，模板要求记录构建/导入/审计摘要。
- [ ] 模板能引用 Sprint 014/015/016 复盘中的媒体链路风险，避免只验证 UI 表象。
