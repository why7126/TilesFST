# 用户故事

## US-001 小程序用户快速浏览商品图片

作为微信小程序用户，我希望商品列表和商品详情首屏优先加载轻量图片，以便在网络较慢或冷启动时也能尽快看到商品信息。

验收要点：

- 列表页商品图片优先使用 `thumbnail_url`。
- 商品详情普通展示优先使用 `display_url`。
- 首屏外图片启用 lazy-load 或等价延迟加载策略。
- 缺失目标规格时按统一 fallback 顺序展示，不出现空白或无限重试。

## US-002 小程序用户查看高清预览

作为微信小程序用户，我希望点击商品图片预览时仍能查看高清图片，以便确认砖面纹理、色差和细节。

验收要点：

- 图片预览使用 `original_url` 或等价高清 URL。
- 预览 URL 与普通展示 URL 可独立配置或派生。
- 预览失败时有明确失败态或 fallback，不影响返回详情页继续浏览。

## US-003 管理端用户上传后自动获得多规格图

作为企业管理端用户，我希望上传商品图片后系统自动生成列表、详情和预览所需的多规格图，以便不需要手工处理多份图片。

验收要点：

- 新上传图片保留 `original`，并生成 `thumbnail` 与 `display`。
- 上传控件具备 `idle -> uploading -> done / failed` 状态。
- 同一会话内上传成功后可看到新媒体或派生图回显。
- 生成失败不暴露内部路径或存储细节，并有可定位错误摘要。

## US-004 后端维护者治理历史媒体

作为后端或平台维护者，我希望能判断存量媒体是否缺少多规格图，并按 dry-run / apply 模式补生成，以便安全处理历史对象。

验收要点：

- dry-run 输出待处理数量、跳过原因和风险分类。
- apply 显式触发，具备幂等性、失败统计和重试建议。
- 输出脱敏 key、资源类型和统计摘要，不包含真实密钥、本机路径或客户数据。
- 能区分只生成派生对象与需要修改数据库记录的场景。

## US-005 测试人员验证媒体链路真实收益

作为测试人员，我希望验收材料同时覆盖 key、object、URL、render 和资源体积/耗时，以便证明小程序和 Web 端真的使用了合适规格图片。

验收要点：

- 记录 `thumbnail / display / original` 的对象存在性、MIME、size 和 URL 类型。
- 记录小程序 DevTools、体验版或真机 Network evidence。
- 记录列表、详情和预览三个场景的实际渲染结果。
- 缺少端上证据时标记 `blocked` 或 `follow_up`，不得写作已通过。
