# 一句话

系统应支持全局缩略图体积目标上限，并在管理后台“系统设置 - 媒体与存储”中配置；默认保持当前不限制模式，开启后对 SKU、品牌、Banner 与证书图片的新生成缩略图生效。

# 原始描述

整理 `/opsx-explore` 中关于缩略图体积控制的需求点：

- 新增全局缩略图大小上限配置，默认不限制，保持当前缩略图生成模式。
- 管理后台“系统设置 - 媒体与存储”应提供该配置入口。
- 配置对所有后端生成的图片缩略图生效，包括 SKU 图片、品牌 Logo、Banner 图片与品牌证书图片。
- 该策略只影响缩略图内容的编码质量、尺寸和最终体积，不改变现有 `.thumb` 缩略图 Key / URL 推导规则。
- 管理后台调整配置后默认仅对增量生效；历史缩略图不得在保存设置时自动重建。
- 历史缩略图如需应用新策略，应通过受控维护任务扫描并重生成。
- 无法压缩到目标上限时，不应阻断原图上传，应记录 warning 或可观测日志。

# 背景与关联

- 背景：当前 FST 项目缩略图生成按尺寸和固定质量输出，不限制最终文件大小；小程序与图片密集列表对缩略图流量较敏感。
- 现状线索：TilesJC 旧工具曾提供按目标 KB 递减质量的离线压缩思路；FST 当前已具备上传链路缩略图生成、同目录 `.thumb` 命名、对象存储适配和维护任务基础。
- 涉及端：后端媒体模块、Web 管理端、小程序展示端间接受益。
- 涉及能力：媒体上传、缩略图生成、系统设置、对象存储、维护任务、OpenAPI / Orval。
- 业务价值：让管理员可以全局控制缩略图流量成本，并避免历史资源在保存配置时被不可预期地批量改写。

# 待澄清

- [ ] 缩略图体积上限字段采用 `0` 还是 `null` 表示不限制
- [ ] 目标上限的允许范围是否设为 `0-1024 KB`
- [ ] 配置文案是否使用“目标上限 / 尽量不超过”，避免承诺复杂图片必达
- [ ] PNG 缩略图是否保持原格式，还是允许在开启体积上限时转为 WebP
- [ ] 是否需要第一版提供后台手动触发历史缩略图扫描/重生成入口，还是仅保留命令行维护任务
- [ ] 历史缩略图重生成是否需要 dry-run 预览影响数量、失败原因和对象存储写入数量
- [ ] 是否需要对缩略图未达标记录可检索的任务链路或审计日志

# 探索结论

- 需求应作为单条全局媒体设置需求处理，不按 SKU、品牌、证书拆分。
- 第一版建议默认只对增量生效；历史缩略图通过受控维护任务处理。
- 不建议改变 `xxx.webp -> xxx.thumb.webp` 的缩略图 URL / Key 推导约定；本需求只改变生成内容，不改变资源寻址模型。
