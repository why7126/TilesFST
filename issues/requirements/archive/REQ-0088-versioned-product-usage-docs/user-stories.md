# 用户故事

## US-001 公开读者浏览版本化产品文档

作为店主、客户或公开访客，我希望通过 `域名/docs` 查看当前版本和历史版本的产品使用文档，以便确认当前版本有哪些功能入口、操作说明和注意事项。

验收要点：

- 文档站导航包含当前版本产品使用文档和发布公告。
- 历史版本文档可以从版本导航或等价入口访问。
- 公开产品文档不得包含密钥、真实客户数据、内部连接串或不可公开运维信息。

## US-002 发布负责人确认发版文档完整性

作为产品负责人或项目负责人，我希望 `/release-prepare <version>` 先确认本次是否需要生成或更新产品使用文档，以便需要时生成与 `release.json` 一致的文档快照，不需要时明确记录跳过原因。

验收要点：

- `release.json` 记录 `usage_docs` 元数据和 generation decision。
- 需要生成或更新时，`release.json` 记录 `usage_docs_preview` gate 证据。
- 不需要生成或更新时，`release.json` 记录 `usage_docs` skipped 状态、确认来源和跳过原因。
- 发布准备失败时能说明产品文档缺失、过期、导航缺页或 broken links 的原因。

## US-003 开发维护文档生成与校验命令

作为开发人员，我希望产品文档生成和校验具备明确命令或脚本，以便在实现和回归时复用同一套输入、输出和错误判定。

验收要点：

- 存在 `/usage-docs-generate <version>`、`/usage-docs-validate <version>` 或等价脚本能力。
- 生成命令读取 `releases/<version>/release.json`，并在用户确认需要后写入当前版本 `usage-docs/`。
- 校验命令检查 manifest、Mintlify 导航、broken links、安全扫描和文档覆盖。

## US-004 实施使用版本一致的培训材料

作为实施或运维人员，我希望每个发布版本的产品使用文档能保留该版本的实际功能说明，以便上线培训和问题回溯时不被新版本文档覆盖。

验收要点：

- 已发布版本的产品内容默认按快照语义维护。
- 自动化不得在无明确授权时改写旧版本产品行为说明。
- 旧版本可进行非内容性维护和安全修复，并保留变更留痕。

## US-005 AI Agent 按发布治理边界生成文档

作为 AI Agent，我希望规则和 Skill 明确产品文档生成、更新和旧版本维护策略，以便不会把未评审内容写入正式文档，也不会在无授权时改写历史版本产品语义。

验收要点：

- 生成当前版本文档前必须确认本次需要生成或更新；生成时以 `release.json` 正式范围为事实源。
- 未评审、未归档或未进入正式发布范围的 REQ / BUG / Change 不进入正式产品使用文档。
- 旧版本内容性更正需要记录原因、操作者、时间、文件范围和变更说明。

## US-006 评审者追踪文档来源和覆盖

作为评审者，我希望通过 `usage-docs/manifest.json` 追踪产品文档的生成来源、输入文件、页面清单、覆盖结果和人工覆盖记录，以便在 Review 中确认文档可信。

验收要点：

- manifest 记录版本、生成时间、来源版本、输入文件、页面清单和覆盖摘要。
- manifest 能标识人工修改和自动化维护策略。
- 发布校验能基于 manifest 发现输入漂移或覆盖缺口。
