# REQ-0079 管理端瓷砖 SKU 列表新增发布时间列

## 1. 需求背景

管理端瓷砖 SKU 列表当前已展示“更新时间”，用于帮助运营判断 SKU 最近一次被维护的时间。但在日常上架、内容巡检和商品管理中，运营也需要知道 SKU 首次发布或进入发布态的时间，以区分“发布时间”和“后续维护时间”。

如果列表只展示更新时间，运营需要进入详情、编辑页或依赖其他上下文才能判断 SKU 的发布节奏，容易影响新品排查、批量巡检和问题沟通效率。因此，本需求要求在管理端瓷砖 SKU 列表中，于“更新时间”前新增“发布时间”列，并保持时间格式与“更新时间”一致。

## 2. 目标用户

| 用户 | 核心诉求 |
|---|---|
| 后台运营 | 在 SKU 列表中直接查看商品发布时间，快速判断新品发布节奏和维护状态。 |
| 后台管理员 | 在排查商品状态、内容更新和发布记录时区分发布时间与更新时间。 |
| 产品 / 业务负责人 | 通过列表快速了解 SKU 发布先后与运营维护情况，减少额外查询成本。 |
| 开发 / 测试人员 | 明确发布时间字段展示位置、格式和接口影响，降低实现与验收歧义。 |

## 3. 需求目标

- 管理端瓷砖 SKU 列表在“更新时间”列前新增“发布时间”列。
- “发布时间”列的时间展示格式必须与现有“更新时间”列保持一致。
- 列表中每个 SKU 都应能展示其发布时间；无发布时间时必须有稳定兜底展示。
- 新增列不得改变现有“更新时间”的含义、数据来源和展示格式。
- 若现有列表接口未返回发布时间字段，实现阶段必须同步后端响应、OpenAPI、Orval、前端类型和测试。
- 本需求只覆盖列表展示，不扩展发布时间筛选、排序、导出或发布流程。

## 4. 范围

### 4.1 本期包含

| 范围 | 说明 |

| 列位置调整 | “发布时间”列位于“更新时间”列之前。 |
| 时间格式一致 | “发布时间”使用与“更新时间”完全一致的日期时间格式、空值格式和视觉样式。 |
| 空值兜底 | 未发布或暂无发布时间的 SKU 必须展示统一占位，不得显示异常字符串。 |
| 数据来源确认 | 实现阶段需确认发布时间字段来源，优先使用后端已存在的发布态时间字段。 |
| 接口契约同步 | 若列表响应缺少发布时间字段，需同步 API Schema、OpenAPI、Orval 与前端调用。 |
| 回归测试 | 覆盖列表列头、列顺序、时间格式、空值展示和接口字段映射。 |

| 不包含 | 说明 |
|---|---|

| 批量导出 | 不调整 SKU 导出字段。 |
| 发布流程改造 | 不新增发布审批、定时发布、重新发布或发布撤回流程。 |
| 店主 Web / 小程序展示 | 不调整公开端或小程序商品列表、详情页的发布时间展示。 |
| 数据迁移清洗 | 不对历史 SKU 发布时间做批量推断或修复；历史空值按统一占位展示。 |

## 5. 核心概念

### 5.1 发布时间

“发布时间”表示 SKU 对业务用户进入发布态的时间。具体字段来源需在实现阶段根据现有数据模型确认，优先级如下：

1. 已存在且语义明确的 SKU 发布时间字段。
2. 已存在发布状态变更记录中的首次发布时间。
3. 若系统暂未记录发布时间，则必须在 OpenSpec Change 中明确是否新增字段或采用兼容兜底。

不得直接把“更新时间”等同为“发布时间”，以免两列展示相同但语义不同的数据。

### 5.2 更新时间

“更新时间”继续表示 SKU 最近一次被修改或维护的时间。本需求不得改变更新时间字段来源、格式、排序或现有展示逻辑。

## 6. 功能要求

### FR-001 列表列展示

- 管理端瓷砖 SKU 列表 MUST 新增“发布时间”列。
- “发布时间”列 MUST 位于“更新时间”列之前。
- 新增列 MUST 与现有列表表格结构、列间距、文字样式和对齐方式保持一致。
- 新增列 MUST 不遮挡 SKU 名称、品牌、类目、状态、更新时间和操作列等既有核心信息。
- 如果列表支持横向滚动或响应式列布局，新增列 MUST 纳入现有布局策略。

### FR-002 时间格式

- “发布时间”的格式 MUST 与“更新时间”列保持一致。
- 如果“更新时间”当前展示秒级时间，“发布时间”也 MUST 展示秒级时间。
- 如果“更新时间”当前使用本地时区格式化，“发布时间”也 MUST 使用相同格式化函数和时区策略。
- 前端 SHOULD 复用现有更新时间格式化工具或渲染逻辑，避免出现格式差异。
- 发布时间为空、缺失或不可解析时，MUST 使用与管理端列表一致的空值占位，例如 `-`。

### FR-003 字段语义与数据来源

- 系统 MUST 明确发布时间字段来源，不能用“更新时间”冒充发布时间。
- 若 SKU 已发布且后端存在发布时间，列表 MUST 展示该发布时间。
- 若 SKU 未发布或暂无发布时间，列表 MUST 展示统一占位，不得展示 `null`、`undefined`、`Invalid Date` 或空白塌陷。
- 若实现需要新增发布时间字段，后端 MUST 保证字段只读语义或由发布流程维护，前端不得允许运营在列表中直接手工编辑。

### FR-004 API 与契约

- 若现有管理端 SKU 列表响应已包含发布时间字段，前端 MUST 复用该字段并保持类型兼容。
- 若现有响应不包含发布时间字段，后端 MUST 在管理端 SKU 列表响应中补充发布时间字段。
- API 响应字段命名 MUST 与现有 SKU 时间字段命名风格一致。
- 如新增或修改 API 字段，MUST 同步 OpenAPI、Orval、前端生成类型、接口文档和相关测试。
- 错误响应、鉴权和分页结构不得因新增字段发生变化。

### FR-005 列表行为保持

- 新增“发布时间”列后，SKU 列表分页、关键词搜索、品牌/类目筛选、状态筛选和操作按钮 MUST 保持原有行为。
- 新增列不得改变默认排序规则。
- 列表加载中、空列表、接口失败等状态 MUST 保持现有展示方式。
- 发布时间字段缺失时不得导致整行渲染失败。

### FR-006 权限与安全

- 发布时间字段只在管理端授权 SKU 列表接口中展示，不绕过既有管理端鉴权。
- 前端不得直连数据库、对象存储或未授权接口获取发布时间。
- 日志、错误提示和 URL 参数中不得额外暴露敏感字段。
- 新增字段不得引入跨租户、跨权限范围的数据可见性变化。

### FR-007 测试与验收支撑

- 前端测试 MUST 覆盖“发布时间”列头存在且位于“更新时间”前。
- 前端测试 MUST 覆盖发布时间格式与更新时间格式一致。
- 前端测试 MUST 覆盖发布时间为空时的占位展示。
- 若调整后端响应，后端测试 MUST 覆盖列表响应包含发布时间字段、字段类型和空值场景。
- 若同步 OpenAPI/Orval，MUST 运行生成与类型检查，并避免手改生成物。

## 7. UI 约束

- 页面继续复用管理端 SKU 列表现有布局，不新增说明区、卡片区或营销式内容。
- “发布时间”列标题、字体、颜色、行高、对齐方式应与“更新时间”列一致。
- 列顺序应形成稳定阅读路径：业务核心字段、状态字段、发布时间、更新时间、操作。
- 宽度不足时应遵循现有表格横向滚动或列宽策略，不得压缩到时间文本重叠。
- 时间文本过长时按现有时间列策略处理，不单独引入新的换行或截断规则。
- 所有颜色和状态样式必须使用 Design System semantic token，不得新增裸 Hex。

| Pydantic Schema | 若列表响应缺少发布时间，需要补充管理端 SKU 列表响应字段。 |

| 小程序 | 本期不涉及。 |
| 店主 Web | 本期不涉及。 |
| 测试 | 需覆盖列顺序、字段映射、时间格式、空值和列表行为回归。 |
