# 用户故事

## US-001 后台运营查看 SKU 发布时间

作为后台运营，我希望在管理端瓷砖 SKU 列表中直接看到每个 SKU 的发布时间，以便快速判断商品发布节奏和新品维护情况。

验收要点：

- SKU 列表存在“发布时间”列。
- “发布时间”列位于“更新时间”列之前。
- 发布时间使用与更新时间一致的日期时间格式。
- 未发布或暂无发布时间的 SKU 有统一占位展示。

## US-002 后台管理员区分发布与维护时间

作为后台管理员，我希望列表同时展示发布时间和更新时间，以便在排查商品状态、内容变更和运营反馈时区分首次发布与后续维护。

验收要点：

- “发布时间”不复用“更新时间”的字段语义。
- “更新时间”原有展示和行为不被改变。
- 列表中同一行能同时查看发布时间与更新时间。
- 发布时间缺失不影响该行其他字段和操作展示。

## US-003 测试人员验证列表列顺序与格式

作为测试人员，我希望发布时间列有明确的列顺序、格式和空值规则，以便编写稳定的前端与接口回归测试。

验收要点：

- 测试能断言“发布时间”列头出现在“更新时间”列头之前。
- 测试能断言发布时间和更新时间使用同一格式化策略。
- 测试能覆盖发布时间为空、缺失或不可解析时的占位展示。
- 如接口新增字段，测试能覆盖响应字段和前端映射。

## US-004 开发人员保持接口兼容

作为开发人员，我希望在实现前明确发布时间字段来源和契约影响，以便判断是否需要后端字段、OpenAPI、Orval 和数据库同步。

验收要点：

- 实现阶段必须确认 SKU 列表响应是否已有发布时间字段。
- 若已有字段，前端复用现有字段并保持类型兼容。
- 若缺少字段，后端响应、Pydantic Schema、OpenAPI、Orval 和测试同步更新。
- 不改变分页、筛选、默认排序、鉴权和错误响应结构。

## US-005 产品负责人确认管理端列表一致性

作为产品负责人，我希望新增时间列后 SKU 列表仍保持管理端列表页一致性，以便避免分页、toast、确认弹窗和宽表布局回归。

验收要点：

- 分页 DOM 与用户管理基准一致。
- 操作成功或失败反馈使用 fixed toast，不引起页面布局位移。
- 本需求不新增危险状态变更；若后续涉及上架/下架、删除等危险操作，必须使用 DS confirm modal。
- 页面不得使用 `window.confirm`。
- 1440x1024 与窄屏视口下，新增时间列不遮挡核心字段和操作列。
