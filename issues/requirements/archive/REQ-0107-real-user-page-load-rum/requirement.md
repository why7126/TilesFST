# REQ-0107 微信小程序和 Web 页面真实用户加载耗时监控

## 1. 需求背景

当前项目已具备日志审计、客户端请求标识和链路观测相关基础能力，但页面体验层面的“真实用户加载耗时”仍缺少统一采集口径。调试阶段可以通过浏览器 DevTools、Lighthouse 或微信开发者工具观察单次加载表现，但这些结果无法持续反映真实用户在不同设备、网络、页面和版本下的体验。

微信小程序和 Web 页面承载店主查看商品、品牌、证书、搜索以及企业内部管理等核心路径。若页面首屏接口慢、资源加载慢、版本发布后性能波动或某类网络环境表现异常，当前缺少按页面和端类型聚合的量化指标，排查容易依赖人工复现和零散反馈。

本需求用于建设轻量自建 RUM 能力，采集真实用户页面加载耗时与关键体验节点，并通过后端受控上报和聚合，为后续管理端性能看板、发布回归和体验优化提供事实依据。

## 2. 目标用户

| 用户 | 诉求 |
|---|---|
| 产品负责人 | 了解小程序与 Web 关键页面的真实加载体验，判断体验优化优先级。 |
| 研发 / 运维人员 | 通过页面、版本、网络、设备等维度定位慢页面、慢接口和性能波动。 |
| 测试人员 | 在发布前后对比关键页面加载指标，验证性能回归风险。 |
| 系统管理员 | 在授权范围内查看管理端或公开端页面性能概览，辅助线上问题反馈定位。 |

## 3. 范围

### 3.1 本期包含

- 采用轻量自建 RUM，不依赖第三方 APM/RUM 平台作为首期必选项。
- Web 端采集真实用户页面导航、首屏可用、关键接口、关键资源或等价加载耗时。
- 微信小程序采集页面进入、首个关键接口完成、首屏渲染就绪、页面可交互或等价加载耗时。
- 后端提供受控性能上报入口，接收匿名化、结构化的页面性能事件。
- 性能事件记录端类型、页面标识、版本、网络类型、设备类别和指标耗时等最小必要字段。
- 后端支持按端类型、页面、版本和时间范围聚合 P50/P75/P95/P99 或等价分位指标。
- 采集与上报必须具备采样、失败降级和隐私脱敏策略。
- 后续管理端可基于该能力查看慢页面排行、页面性能趋势和版本对比。

### 3.2 本期不包含

- 不接入第三方 APM、RUM、OpenTelemetry、Jaeger 或云监控平台作为强制依赖。
- 不建设实时大屏、自动告警、SLA 报表或复杂 BI 分析。
- 不采集手机号、openid、Authorization、Cookie、签名 URL、真实客户数据或完整请求/响应体。
- 不将客户端上报字段作为服务端鉴权或可信身份依据。
- 不要求首期覆盖所有页面；具体首批页面在 `/req-complete` 阶段确认。
- 不要求对历史页面性能进行回填统计。
- 不包含视频转码、图片压缩、多清晰度资源优化等媒体处理增强能力。

## 4. 功能要求

### FR-001 Web 真实用户加载指标采集

Web 端 MUST 在统一前端入口或路由层采集页面加载与首屏体验指标。

Web 指标 SHOULD 覆盖：

| 指标 | 说明 |
|---|---|
| 页面导航耗时 | 基于浏览器 Performance Navigation Timing 或等价 API 计算页面导航阶段耗时。 |
| 首屏可用耗时 | 从页面进入到关键内容可见或业务自定义 `first_content_ready` 的耗时。 |
| 完整加载耗时 | 浏览器 load 事件或等价完整加载节点耗时，作为辅助指标。 |
| 关键接口耗时 | 首屏主接口、列表接口、详情接口等对可用性有直接影响的 API 耗时。 |
| 关键资源耗时 | 首屏图片、样式、脚本或业务指定资源的加载耗时，采集范围需受控。 |

Web 采集 MUST 区分管理端和店主展示端，不得混淆权限边界。若首期只覆盖其中一端，必须在后续需求完善阶段明确范围和延后项。

### FR-002 微信小程序真实用户加载指标采集

微信小程序 MUST 在 App、页面生命周期或统一页面性能工具中采集关键加载节点。

小程序指标 SHOULD 覆盖：

- 页面进入时间；
- `onLoad`、`onShow`、`onReady` 或等价生命周期节点；
- 首个关键业务接口完成时间；
- 首屏渲染就绪时间；
- 页面可交互时间；
- 关键接口失败、超时或降级状态。

小程序采集 MUST 适配微信小程序运行环境，不得依赖 Web 浏览器专属 API。行为上报失败不得阻断页面展示、搜索、列表、详情、上传或其他主业务流程。

### FR-003 统一性能事件模型

系统 MUST 定义统一性能事件模型，用于承载 Web 与微信小程序的 RUM 数据。

性能事件 SHOULD 至少包含：

| 字段 | 说明 |
|---|---|
| `client_type` | 端类型，例如 `web_admin`、`web_catalog`、`wechat_miniapp`。 |
| `page_key` | 受控页面标识，不使用完整可变 URL 暴露敏感参数。 |
| `app_version` | 前端或小程序版本，用于版本对比。 |
| `network_type` | 网络类型或未知值。 |
| `device_class` | 设备类别或受控归类，不采集精确设备指纹。 |
| `metric_name` | 指标名，例如 `first_content_ready`、`full_load`、`first_api_done`。 |
| `duration_ms` | 指标耗时，单位毫秒。 |
| `sample_rate` | 本次采样率或采样策略标识。 |
| `occurred_at` | 客户端事件发生时间；服务端仍需记录接收时间。 |

事件模型 MUST 限制字符串长度、枚举值和数值范围，避免日志污染、超长字段和异常 payload。

### FR-004 后端性能上报接口

后端 MUST 提供受控性能上报接口或等价能力，用于接收端侧 RUM 事件。

上报能力 MUST 满足：

- 公开端与小程序可在不暴露管理端权限的前提下上报匿名性能事件；
- 管理端上报仍遵守现有鉴权与权限边界；
- 请求体使用 Pydantic Schema 校验字段、枚举、长度和数值范围；
- 对无效 payload 返回统一错误响应和错误码；
- 上报接口不得记录 Authorization、Cookie、手机号、openid、签名 URL 或完整请求/响应体；
- 上报失败不得影响端侧主流程；
- 支持批量上报或节流策略，避免大量单条请求放大服务压力。

API 变更在 OpenSpec 阶段 MUST 同步 OpenAPI、Orval、接口文档和测试。

### FR-005 数据聚合与查询

系统 MUST 支持对性能事件进行基础聚合，支撑后续管理端查看和研发排障。

聚合能力 SHOULD 支持：

- 按时间范围筛选；
- 按端类型、页面、版本、网络类型和设备类别筛选；
- 输出请求量、样本量、平均耗时、最大耗时和 P50/P75/P95/P99；
- 输出慢页面排行和慢指标排行；
- 对样本不足的页面或维度标识统计口径不足；
- SQLite demo 和生产 MySQL 均可运行。

实现阶段 MUST 评估数据量、索引和保留周期，避免长期性能事件无限增长影响业务数据库。

### FR-006 采样、降级与隐私

系统 MUST 提供采样、降级与隐私保护策略。

策略要求：

- 支持默认采样率，避免所有用户、所有页面、所有指标全量上报造成压力；
- 支持按端、页面或版本调整采样策略，具体配置方式在 OpenSpec 阶段确认；
- 端侧 RUM 上报失败、超时或被限流时，不得影响页面主流程；
- 不采集可直接识别个人身份的字段；
- 不采集完整 URL 查询参数、签名 URL、请求体、响应体、Header、Cookie 或 Token；
- 对页面路径、接口路径和资源标识使用受控 key 或脱敏值；
- 管理端查询性能数据必须受权限控制。

### FR-007 管理端性能观测入口

系统 SHOULD 在管理端提供真实用户性能观测入口，或为后续看板预留结构化查询接口。

若本期包含管理端页面，页面 SHOULD 支持：

- 性能摘要指标；
- 慢页面排行；
- 页面趋势；
- 版本对比；
- 端类型、页面、时间范围、网络类型筛选；
- 空数据、加载失败、样本不足和权限不足反馈。

若本期不包含管理端页面，后端接口和数据结构 MUST 能支撑后续管理端看板，不得只将 RUM 数据写入不可查询日志。

## 5. UI 约束

- 管理端性能观测页面 MUST 遵守“工业石材 · 暗色旗舰风” Design System，使用 semantic token 与既有管理端组件。
- 页面 SHOULD 复用现有管理端筛选区、指标卡、表格、趋势图或等价组件。
- 指标展示 MUST 以排障和对比为目标，避免只放装饰性图形。
- 分位耗时、慢页面排行和版本对比需要清楚标注统计口径和样本量。
- 字段较长时应截断展示并提供受控复制，避免撑破表格布局。
- 小程序和店主 Web 前台首期不要求新增可见 UI；若出现性能上报失败，不应向普通用户暴露内部监控细节。
