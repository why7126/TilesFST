# User Stories

## US-001 管理端请求客户端归因

作为系统管理员，我希望日志审计中管理端 API 请求稳定显示为 `web_admin`，以便排查内部员工操作时不被误归因到店主前台或小程序。

验收要点：

- 管理端 API 请求携带统一客户端类型。
- 后端请求日志记录 `client_type=web_admin`。
- 日志审计列表或详情可看到该客户端类型。

## US-002 店主 Web 前台请求客户端归因

作为开发 / 运维人员，我希望店主 Web 前台 API 请求稳定显示为 `web_catalog`，以便区分公开展示端访问与企业内部管理端操作。

验收要点：

- 店主 Web 前台 API 请求携带统一客户端类型。
- 后端请求日志记录 `client_type=web_catalog`。
- 未登录或匿名访问不得绕过后端授权与公开数据边界。

## US-003 微信小程序普通 API 请求归因

作为测试人员，我希望微信小程序普通 API 请求稳定显示为 `wechat_miniapp`，以便验证小程序行为事件与普通业务请求的客户端来源一致。

验收要点：

- 小程序统一 request 封装注入客户端类型。
- 普通 API 请求与 usage-events 上报使用一致的客户端类型枚举。
- fallback base URL 重试策略需有明确请求标识复用或重建规则。

## US-004 后端可信 request_id 与客户端请求 ID 区分

作为开发 / 运维人员，我希望后端可信 `request_id` 与客户端生成的请求标识分开记录，以便在排障时既能追踪服务端链路，又不误信任客户端可伪造字段。

验收要点：

- 后端每次请求继续生成可信 `request_id`。
- 响应头返回后端可信 `x-request-id`。
- 客户端请求标识以独立字段或 metadata 保存。
- 日志审计字段命名能区分两类 ID。

## US-005 行为事件关联业务请求

作为产品负责人，我希望可从用户行为事件追溯到相关业务请求，以便分析一次用户动作背后的接口请求和失败原因。

验收要点：

- 行为事件可携带相关后端 `request_id` 或客户端请求标识。
- 行为事件上报失败不阻断主业务流程。
- 后端不信任前端传入的用户身份、角色或权限字段。

## US-006 日志审计展示与复制请求标识

作为系统管理员，我希望在日志审计列表或详情中查看并复制请求标识，以便把排障信息快速交给开发 / 运维人员。

验收要点：

- 列表或详情展示客户端类型、后端可信 `request_id`、客户端请求标识。
- 长 ID 在列表中截断但可复制完整值。
- 复制反馈使用 fixed toast，不引发布局位移。
