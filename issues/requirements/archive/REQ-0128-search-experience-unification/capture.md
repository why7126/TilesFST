# 一句话

搜索体验统一优化：强化首页搜索入口，并统一小程序与管理端主要列表搜索能力。

# 原始描述

用户希望将两个搜索相关想法合并推进：

- 搜索体验统一优化：首页搜索入口强化，并为小程序与管理端主要列表补齐一致的搜索能力。
- 小程序搜索入口组件化与多页面复用：统一各页面搜索入口，复用现有搜索页承接搜索首页、联想和结果页。

# 拆分判断

本次按 1 条 REQ 记录。两个想法同属“搜索体验统一”功能域，围绕用户找砖、查品牌、查证书和管理端列表检索的同一体验链路展开；搜索入口组件化是实现搜索体验统一的手段之一，不宜拆成独立 peer REQ。

# 待澄清

- [ ] MVP 是否覆盖小程序和管理端两端，还是先做小程序端。
- [ ] 小程序各页面采用“统一入口跳转完整搜索页”为主，还是同步支持当前列表内搜索。
- [ ] 管理端列表范围是否限定品牌、类目、SKU、规格、Banner、证书、用户、日志等主要列表。
- [ ] 是否需要新增或调整后端列表查询参数；若需要，需同步 OpenAPI / Orval / API 文档 / 测试。
- [ ] 搜索行为埋点字段是否以现有搜索事件为基线扩展，还是同步治理成统一事件字典。

# 探索结论

- 小程序现有 `search-entry` 已是输入组件，但完整搜索首页、联想、结果、筛选和埋点主要集中在 `/pages/search/index` 页面内。
- 首页当前存在自定义搜索框入口，但尚未与 `search-entry` 形成统一组件复用。
- 搜索页可以作为完整搜索体验承接页被各页面通过参数复用；不建议把完整搜索结果页嵌入每个列表页。
- 列表内搜索应与全局搜索分层：全局搜索用于跨 SKU、品牌、类目、证书查找；列表内搜索用于当前列表范围筛选。
- 本需求涉及行为埋点、请求来源、结果曝光和可能的 API 查询参数，后续 PRD 与 Change 必须声明产品数据采集与链路观测适用性。
