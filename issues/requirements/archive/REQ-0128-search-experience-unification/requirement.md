# REQ-0128 搜索体验统一优化

## 1. 需求背景

当前小程序已经具备完整搜索页，包含搜索首页、关键词联想、综合结果、分区结果、筛选、历史搜索、热门搜索、无结果推荐和结果曝光埋点；同时也已经存在 `search-entry` 输入组件和 `product-card` 商品卡片组件。

但从用户找砖路径看，搜索体验还没有形成统一产品规范：小程序首页搜索入口与 `search-entry` 组件未统一，品牌、证书、商品列表等页面对搜索入口的承接不一致；搜索页本身可以作为完整搜索体验承接页复用，但搜索结果页不是可嵌入到各页面的独立组件。底部 Tab「全部分类」页定位为结构化分类浏览频道，不纳入搜索入口铺设范围。管理端列表页已有搜索/筛选基础，但不同主要列表页的关键词入口、筛选区布局、重置行为和查询参数能力仍需要统一。

本需求要求把“首页搜索入口强化”“小程序搜索入口组件化与多页面复用”“小程序与管理端主要列表搜索能力补齐”合并为一个搜索体验统一需求，建立用户可理解、开发可复用、验收可观测的搜索体系。

## 2. 目标用户

| 用户 | 核心诉求 |
|---|---|
| 装修客户 | 在小程序首页、品牌、证书和商品列表中快速发起搜索，减少反复返回首页或切换 Tab 的成本；在全部分类页通过分类层级浏览找砖。 |
| 设计师 | 按品牌、规格、型号、类目或证书快速定位资料，便于现场选型和对比。 |
| 门店导购 | 在演示过程中快速从任意页面进入搜索，查找客户提到的产品、品牌或规格。 |
| 企业管理人员 | 在管理端主要列表中用一致的关键词搜索和筛选方式查找品牌、类目、SKU、规格、Banner、证书、用户和日志。 |
| 产品与运营人员 | 能通过搜索入口点击、搜索提交、结果曝光、无结果和列表筛选数据判断搜索体验是否改善。 |
| QA / 验收人员 | 使用统一范围和观测字段验证小程序、管理端、API 和埋点是否一致。 |

## 3. 需求目标

- 强化小程序首页搜索入口，使搜索成为首页首屏的高权重找砖入口。
- 统一小程序各主要页面的搜索入口组件和跳转参数，复用现有搜索页承接完整搜索体验。
- 明确全局搜索与列表内搜索的分层：全局搜索跨 SKU、品牌、类目、证书；列表内搜索仅过滤当前列表范围。
- 为小程序主要列表补齐搜索入口或列表内搜索能力，避免用户只能浏览不能快速查找。
- 统一管理端主要列表的关键词搜索、筛选区位置、重置行为和空结果反馈。
- 若新增或调整 API 查询参数，必须同步后端校验、OpenAPI、Orval、API 文档和测试。
- 搜索相关行为事件、请求链路、来源页面、关键词脱敏和结果数量必须纳入验收。

## 4. 范围

### 4.1 本期包含

| 范围 | 说明 |
|---|---|
| 小程序首页搜索入口 | 首页搜索入口强化，视觉权重和位置需体现“找砖主入口”。 |
| 小程序搜索入口复用 | 优先复用或增强 `components/search-entry/`，统一 placeholder、来源页面、scope、提交、清空和取消事件。 |
| 小程序完整搜索页复用 | 继续以 `/pages/search/index` 承接搜索首页、关键词联想、搜索结果、筛选、分页、历史和无结果态。 |
| 小程序多页面入口 | 证书页、商品列表页、收藏页等主要页面应能快速进入搜索；品牌列表页采用当前页品牌字段过滤；全部分类页不展示搜索入口。 |
| 小程序列表内搜索策略 | 商品列表可结合当前分类、品牌或 section 范围搜索；品牌列表按品牌名称、品牌简称和品牌英文名在当前页过滤，证书等列表按业务对象提供关键词查找。 |
| 管理端主要列表搜索统一 | 品牌、类目、SKU、规格、Banner、证书、用户、日志等主要列表统一关键词搜索、筛选区和重置体验。 |
| 数据采集与链路观测 | 搜索入口点击、搜索提交、联想曝光、结果曝光、无结果、列表筛选和重置行为纳入统一观测口径。 |
| 测试与文档同步 | 涉及端侧、API、Orval、测试或长期文档的变更按后续 Change 范围同步。 |

### 4.2 本期不包含

| 不包含 | 说明 |
|---|---|
| 重建搜索引擎 | 不引入 Elasticsearch、向量搜索、外部搜索服务或复杂分词引擎。 |
| 搜索结果页嵌入所有列表 | 不把完整搜索结果页作为页面内组件嵌到每个列表；完整搜索仍由 `/pages/search/index` 承接。 |
| 搜索词运营后台 | 热门词配置、搜索词报表、运营推荐规则不纳入本期。 |
| 结果高亮和纠错 | 搜索关键词高亮、拼写纠错、同义词管理和相似规格推荐可作为后续增强。 |
| 管理端高级查询 DSL | 不新增复杂组合查询、保存筛选方案或跨表高级检索。 |
| 数据库搜索索引重构 | 除必要查询参数和普通索引评估外，不做大规模 DB 检索模型重构。 |
| 权限边界放宽 | 管理端搜索不得暴露未授权数据；小程序搜索仅返回允许公开的商品、品牌、类目和证书信息。 |

## 5. 功能要求

### FR-001 小程序首页搜索入口必须强化

- 小程序首页 MUST 展示高权重搜索入口，支持用户从首页首屏快速进入搜索。
- 首页搜索入口 SHOULD 复用统一搜索入口组件或与统一组件保持同一交互契约。
- 入口文案 SHOULD 覆盖瓷砖名称、编号、品牌、规格等高频搜索意图。
- 首页搜索入口点击后 MUST 跳转到 `/pages/search/index`，并携带来源页面信息。
- 首页 Banner、快捷入口和商品推荐不得因搜索入口强化产生不可用或明显遮挡。

### FR-002 小程序搜索入口组件必须形成统一契约

- 小程序主要页面 SHOULD 复用同一个搜索入口组件或同一封装能力，避免每个页面私有实现搜索框。
- 组件 MUST 支持 `keyword`、`placeholder`、`scope`、`sourcePage`、`disabled` 等基础属性或等价能力。
- 组件 MUST 输出输入、提交、清空、取消等稳定事件，供搜索页或列表页按场景接入。
- 组件 SHOULD 支持只读入口模式与可输入搜索模式：入口模式点击跳转完整搜索页，可输入模式用于搜索页或列表内搜索。
- 组件视觉 MUST 与小程序当前暗色旗舰风保持一致，避免不同页面出现不同搜索框皮相。

### FR-003 完整搜索体验由搜索页统一承接

- 完整搜索体验 MUST 继续由 `/pages/search/index` 承接，包括搜索首页、热门词、历史搜索、关键词联想、结果分区、筛选、分页和无结果态。
- 各页面跳转搜索页时 SHOULD 传递 `sourcePage`、`scope`、`keyword` 或当前上下文参数，便于搜索页识别来源和默认范围。
- 搜索页 MUST 保持对 SKU、品牌、类目、证书等综合结果的承接能力。
- 搜索页结果卡片可在后续实现中按需要抽象，但不得阻塞本期统一入口和搜索体验闭环。
- 搜索页不得因为多页面接入而破坏现有搜索历史、热门搜索、联想和结果点击逻辑。

### FR-004 小程序主要列表必须支持搜索路径

- 商品列表页 MUST 支持用户在当前列表上下文下继续搜索，例如当前分类、品牌、section 或关键词结果。
- 底部 Tab「全部分类」页 SHOULD 保持纯分类浏览，不展示全局搜索入口。
- 品牌列表页 SHOULD 支持按品牌名称、品牌简称和品牌英文名在当前页过滤，搜索结果保持品牌列表页卡片布局；搜索态隐藏 Banner 轮播，清空后恢复完整品牌列表和 Banner。
- 证书列表页 SHOULD 支持按证书名称、品牌名称、证书类型枚举或中文类型标签在当前页过滤，搜索结果保持证书卡片布局，不跳完整搜索结果页。
- 收藏页 SHOULD 收敛为当前收藏商品范围内搜索，搜索结果保持收藏卡片布局，并移除或弱化去全局搜索调整入口。
- 小程序列表内搜索结果为空时 MUST 给出明确空态，提示调整关键词、清空当前搜索或按适用场景返回全局搜索。

### FR-005 管理端主要列表搜索体验必须统一

- 管理端主要列表页 SHOULD 统一关键词搜索入口位置、筛选区布局、重置行为和空结果反馈。
- 已使用统一列表模板的页面 SHOULD 优先复用模板搜索能力，不重复造页面私有搜索控件。
- 尚未使用统一模板的页面应在后续设计中说明是接入模板，还是保持页面专属布局但遵守统一搜索契约。
- 关键词搜索字段 SHOULD 与业务对象匹配，例如品牌名称、SKU 名称/编码、类目名称、规格、Banner 位置、证书名称、用户名、日志操作者或路径摘要。
- 管理端搜索 MUST 遵守权限边界，只返回当前登录用户有权查看的数据。

### FR-006 API 查询能力必须按最小范围补齐

- 若现有列表 API 已支持关键词或过滤参数，前端 SHOULD 优先复用既有参数。
- 若小程序品牌、证书、收藏或管理端列表缺少必要关键词参数，后续 Change MUST 明确新增查询参数、长度限制、默认值和错误响应。
- 后端 MUST 对关键词、scope、tab、分页、筛选枚举和范围参数做类型、长度和枚举校验。
- API 变更 MUST 同步 OpenAPI、Orval、`docs/03-api-index.md` 和相关测试。
- 不需要新增 API 的页面必须在 Change 设计中写明复用现有搜索页、现有列表 API 或纯前端过滤的依据。

### FR-007 搜索行为与链路观测必须可验收

- 搜索入口点击、搜索输入停顿、搜索提交、联想曝光、联想点击、结果曝光、结果点击、无结果、列表筛选和重置 SHOULD 采集稳定事件名。
- 行为事件属性 SHOULD 包含来源页面、搜索范围、关键词脱敏摘要、结果数量、选中 Tab、筛选条件摘要和请求 ID。
- 客户端请求封装 SHOULD 透传 `behavior_trace_id`、`behavior_event_id` 或等价链路字段，使搜索行为与后端请求日志可关联。
- 搜索关键词不得以可能包含隐私或敏感信息的原文无限制写入日志；需要按规范脱敏、截断或只保留统计摘要。
- 复杂搜索查询通常不进入 Task Trace；若后续实现判定某类搜索为长耗时复杂查询，应按 Task Trace 覆盖规则声明原因和验证方式。

### FR-008 搜索体验必须具备基础可用性和降级

- 搜索入口在加载态、错误态、空态和正常态的展示规则必须清晰，避免用户在异常状态无法发起搜索。
- 搜索请求失败时 MUST 给出可重试反馈，且不得清空用户已输入关键词。
- 联想接口失败时 SHOULD 降级为可直接提交搜索，不阻断主搜索流程。
- 列表内搜索和全局搜索的文案必须能让用户理解搜索范围。
- 小程序常见手机宽度下搜索入口、列表内容、悬浮按钮和底部 TabBar 不得互相遮挡。

## 6. UI / UE 约束

- 小程序搜索入口视觉 SHOULD 与现有 `search-entry` 保持一致，包含深色搜索底、圆角、弱提示文案和明确可点击区域。
- 首页搜索入口应比普通快捷入口更突出，但不得压过自定义导航栏或遮挡 Banner 操作。
- 列表页搜索入口应靠近列表标题或筛选区域，让用户理解搜索作用于当前页面或当前范围。
- 完整搜索页继续保留搜索首页、联想、结果 Tab、空态推荐和加载更多结构。
- 管理端列表页优先复用 `AdminListPage` 或既有筛选卡片样式，保持关键词、筛选项、重置按钮、分页和空态顺序一致。
- UI 变更不得新增裸 Hex；Web 管理端必须使用 Design System semantic token，小程序样式需沿用当前暗色旗舰风和既有组件样式。
- 按钮、输入框、筛选项和空态文字在移动端与桌面宽度下不得溢出或互相遮挡。

## 7. 数据、接口与测试影响

| 范围 | 影响 |
|---|---|
| 微信小程序 | 影响首页、搜索页、品牌页、证书页、商品列表页、收藏页等搜索入口和跳转参数；全部分类页不展示搜索入口；后续实现需同步 `.ts` 与 `.js`。 |
| Web 管理端 | 影响主要列表页关键词搜索、筛选区和重置体验；需保持管理端权限边界。 |
| 店主 Web | 本期默认不改；如后续纳入店主 Web 展示端，应在 `/req-complete` 或 Change 中扩展范围。 |
| 后端 API | 可能新增或调整小程序与管理端列表查询参数；若发生 contract 变化，必须同步 Pydantic Schema、OpenAPI 和测试。 |
| SQLite / MySQL | 默认不新增表；若搜索性能需要新增普通索引，必须同步 schema、迁移、数据库文档和测试。 |
| Orval | 管理端或店主 Web API contract 变化时需要；纯小程序手写请求不触发 Orval，但后端 OpenAPI 仍需更新。 |
| 行为埋点 / 请求日志 | 适用；搜索入口、提交、筛选、结果曝光和请求链路需按采集规范声明与验证。 |
| Task Trace | 默认不适用普通搜索；若实现中出现长耗时复杂查询或批量任务，应重新评估。 |
| Docker Compose | 默认不需要。 |
| 测试 | 需补充小程序静态/交互检查、管理端列表测试、后端查询参数测试、埋点与链路 ID 透传验证。 |

## 9. 风险与待确认

| 风险 / 待确认 | 说明 |
|---|---|
| 范围过大 | 同时覆盖小程序和管理端，后续 `/req-complete` 需明确 MVP 页面清单，避免一次性扩到所有边缘页面。 |
| 全局搜索与列表内搜索混淆 | 需要在文案、参数和空态中明确搜索范围，避免用户不清楚是在搜全站还是搜当前列表。 |
| API contract 扩散 | 品牌、证书、收藏、管理端列表若都补关键词参数，会带来后端、OpenAPI、Orval 和测试同步成本。 |
| 埋点字段过细 | 需要保留能评估搜索效果的字段，但避免记录完整敏感关键词或过多临时 UI 状态。 |
| 组件抽象边界 | `search-entry` 可作为入口基础，但完整搜索页不是组件；后续实现需避免过度抽象造成页面复杂度上升。 |
| 小程序双文件同步 | 小程序 `.ts` 与 `.js` 并存，后续实现必须同步维护，避免体验版运行入口漂移。 |
