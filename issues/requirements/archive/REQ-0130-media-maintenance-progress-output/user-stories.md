# 用户故事

## US-001 运维人员查看生产维护进度

作为实施 / 运维人员，我希望执行 `backfill-image-variants`、`backfill-brand-certificate-thumbnails` 或 `media-drift-reconcile` 时能看到处理进度，以便判断任务仍在推进、当前完成了多少、是否出现失败，以及是否需要继续等待或中止排查。

验收要点：

- 进度输出展示任务名、阶段、总量、已完成数量、成功数量、失败数量、跳过数量和百分比。
- 进度输出在长时间 apply 中持续更新，不只在命令结束时出现。
- 当任务失败数量增加时，进度输出能反映失败计数。
- 输出内容不包含真实 object key、生产敏感配置或客户信息。

## US-002 自动化脚本保持 JSON 解析兼容

作为发布负责人或脚本维护者，我希望默认命令行为不变，且开启进度后最终 JSON 仍可被 `jq` 和现有生产脚本解析，以便在增强人工可见性的同时不破坏审计和自动化链路。

验收要点：

- 默认不加进度参数时，stdout 只输出现有完整 JSON。
- 开启进度参数后，最终 JSON 仍输出到 stdout。
- 进度信息输出到 stderr 或等价隔离通道。
- Runbook 明确 stdout / stderr 边界和日志采集建议。

## US-003 开发人员复用统一进度机制

作为后端 / 媒体能力开发人员，我希望维护任务使用统一的进度输出结构，以便后续新增维护任务时能复用同一套计数、阶段和脱敏规则。

验收要点：

- 进度输出结构能覆盖 dry-run 扫描、apply 写入、跳过、失败和阶段切换。
- `backfill-image-variants` 能表达单个源图对应多个派生写入的处理口径。
- `media-drift-reconcile` 能表达 4 个子任务的阶段级进度。
- 失败对象定位仍依赖最终 JSON 的脱敏 hash 和失败原因，不通过进度行泄露细节。

## US-004 测试人员验证进度与安全

作为测试 / 验收人员，我希望有明确的验收清单覆盖进度准确性、输出通道、异常计数和敏感信息保护，以便确认该能力可用于生产命令。

验收要点：

- 测试覆盖默认 stdout JSON 兼容。
- 测试覆盖启用进度后的 stderr 输出和 stdout JSON 可解析。
- 测试覆盖成功、失败、跳过和百分比计算。
- 测试覆盖真实 key、`.env`、密钥和连接串不会出现在进度输出中。
