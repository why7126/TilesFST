# 用户故事

## US-001 生产服务器内执行维护任务

作为实施 / 运维人员，我希望能在生产服务器上通过 Docker Compose 一次性容器执行媒体历史维护任务，以便复用生产 env、网络和密钥注入，不需要将生产 `.env` 下载到开发机。

验收要点：

- 能明确生产主入口为 `deploy/prod/compose.tencent-cos.yml`，兼容入口单独说明适用边界。
- 命令示例不输出真实 env、密钥、数据库连接串或对象存储私有 URL。
- 维护任务以 `run --rm` 或等价一次性容器执行，不改变在线服务启动方式。

## US-002 发布负责人确认镜像和 Compose 一致

作为发布负责人，我希望维护任务使用的镜像、Compose 文件和 env 示例都能进入发布治理视野，以便避免生产临时挂载未评审脚本后直接写数据。

验收要点：

- 明确专用 maintenance 镜像 / 服务与复用 backend 镜像的决策边界。
- 维护入口必须来自受控镜像或受控命令，不依赖未追踪的临时本机脚本。
- 若使用只读临时挂载进行应急审计，文档必须标记禁止 apply。

## US-003 后端开发改造历史脚本

作为后端开发，我希望媒体历史脚本能统一使用后端配置、数据库 session 和对象存储适配层，以便同一脚本可以在 MySQL + COS / S3 兼容 provider 环境中安全运行。

验收要点：

- 脚本不得只依赖 SQLite 文件路径或本地 MinIO 默认配置。
- 脚本支持 dry-run / apply 两阶段。
- 对对象 copy、remove、put、stat 的 provider 差异有明确处理或限制说明。

## US-004 测试验收维护结果

作为测试 / 验收人员，我希望每次维护任务都有 dry-run、apply 和二次审计摘要，以便确认 key、object、URL、thumbnail benefit 和 render 没有断链或泄密。

验收要点：

- dry-run 输出受影响数量、跳过原因、缺失对象、目标冲突和风险提示。
- apply 输出成功、失败、跳过、重试候选和失败原因统计。
- 二次审计摘要覆盖媒体四联或五联维度，并区分 passed、failed、blocked、n/a。

## US-005 产品负责人判断上线风险

作为产品 / 业务负责人，我希望能看到历史媒体维护任务的影响范围、回滚方式和用户可见收益，以便决定是否允许进入 Sprint 和生产执行窗口。

验收要点：

- 维护任务执行前要求 MySQL 快照和对象存储 bucket / prefix 快照。
- 回滚说明以恢复快照为主，不承诺未验证反向脚本。
- 对清理历史对象等高风险动作明确排除或要求另行审批。
