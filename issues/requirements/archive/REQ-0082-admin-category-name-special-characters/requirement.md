# REQ-0082 管理后台瓷砖类目名称允许特殊字符

## 1. 需求背景

`REQ-0005-tile-category-management` 定义了瓷砖类目管理基础能力，`REQ-0077-category-name-max-length-15` 已将类目名称长度上限调整为最多 15 个字符，但当前命名规则仍限制为只能包含中文、英文和数字。

产品方反馈，瓷砖类目在实际运营命名中可能需要使用特殊字符表达系列、组合、材质或适用场景，例如连接符、斜杠、括号、点号等。继续限制为中文、英文和数字，会迫使运营使用不自然的替代写法，降低类目主数据的可读性。本需求将管理后台瓷砖类目名称的允许字符范围调整为“中文、英文、数字和特殊字符”，并保持最多 15 个字符的长度限制不变。

本需求是 `REQ-0005-tile-category-management` 的子需求 / refinement，并承接 `REQ-0077-category-name-max-length-15` 的长度规则。除类目名称允许字符范围外，不改变同层级唯一、类目编码自动生成、排序权重、层级上限、启停状态等既有规则。

## 2. 目标用户

- **后台管理员 / 内部员工**：在管理后台新增或编辑瓷砖类目时，可以使用符合业务表达习惯的特殊字符。
- **运营与商品维护人员**：维护 SKU、筛选类目和核对分类树时，可以读取更清晰的类目名称。
- **前台消费方用户**：通过小程序或 Web 展示端查看分类、筛选入口和商品列表时，类目名称应保持可读且布局稳定。

## 3. 范围

### 3.1 本期包含

- 管理后台新增类目、编辑类目弹窗的类目名称校验规则调整为：最多 15 个字符，允许中文、英文、数字和特殊字符。
- 管理后台前端表单即时校验、保存前校验和字段级错误提示同步调整。
- 后端创建 / 更新类目 API 的 Pydantic Schema、Service 层或等价业务校验同步调整，确保服务端兜底接受特殊字符。
- OpenAPI / Orval / API 文档 / 测试在接口契约变化时同步更新。
- 检查并回归管理端类目列表、类目树、类目选择器、小程序分类页、Web 展示端分类入口中对特殊字符类目名称的展示兼容性。
- 测试夹具与最小合法 payload 中如存在“仅中文、英文和数字”的假设，需同步调整。

### 3.2 本期不包含

- 不调整类目名称最多 15 个字符的长度上限。
- 不调整类目名称 trim 后非空规则。
- 不调整同层级类目名称唯一规则。
- 不调整类目编码自动生成策略和编码展示规则。
- 不调整类目层级上限、上级类目选择规则、排序权重规则或启停规则。
- 不做历史类目数据迁移、清洗或批量重命名。
- 不新增类目别名、多语言名称、简称、SEO 名称或展示名称字段。
- 不改变店主端或小程序的类目筛选逻辑；仅要求展示和查询对合法名称保持兼容。

## 4. 功能要求

### FR-001 类目名称字符集放宽

- 管理后台新增类目弹窗中，类目名称字段 MUST 允许输入中文、英文、数字和特殊字符。
- 管理后台编辑类目弹窗中，类目名称字段 MUST 允许输入中文、英文、数字和特殊字符。
- 类目名称最多 15 个字符，trim 后 MUST 非空。
- 字符数按用户可见字符计数，中文、英文、数字和特殊字符均按 1 个字符计算。
- 现有“只能包含中文、英文和数字”的规则 MUST 被替换，不得在前端校验、后端校验、错误提示、测试夹具或文档中继续作为有效约束。
- 特殊字符的最终允许范围在 `/req-complete` 阶段明确；在未进一步收敛前，应至少支持常见业务符号，例如 `-`、`_`、`/`、`&`、`()`、`·`、`.`、`+`、`#`。

### FR-002 后端 API 兜底校验

- 创建类目 API MUST 在服务端接受包含合法特殊字符、长度不超过 15 个字符的类目名称。
- 更新类目 API MUST 在服务端接受包含合法特殊字符、长度不超过 15 个字符的类目名称。
- 后端不得仅依赖前端校验；Pydantic Schema、Service 层或等价业务层 MUST 有兜底校验。
- 如果类目名称为空、超过 15 个字符或包含最终规则禁止的字符，后端 MUST 返回稳定业务错误，且响应结构继续遵守统一 response envelope。
- 如当前错误码仅表达“名称非法”而不区分具体原因，可沿用现有错误码；如新增错误码，MUST 同步错误码文档、OpenAPI 和测试。

### FR-003 输入安全与边界

- 类目名称 MUST 禁止换行、制表符、不可见控制字符和仅由空白组成的输入。
- 类目名称保存前 MUST 去除前后空格；去除后为空时按空名称处理。
- 如果最终规则允许空格，MUST 明确是否允许中间空格；如果不允许，前后端提示需保持一致。
- 前端和后端对特殊字符的允许范围 MUST 保持一致，避免前端可提交但后端拒绝，或后端可接受但前端拦截。
- 不得因放宽特殊字符而绕过鉴权、同层级唯一性、SQL 参数化或统一输入校验要求。

### FR-004 错误提示与表单体验

- 超长错误提示 SHOULD 继续统一为：`类目名称最多 15 个字符`。
- 非法字符错误提示 SHOULD 统一表达为：`类目名称仅支持中文、英文、数字和特殊字符`，最终文案可在 `/req-complete` 阶段按产品口径收敛。
- 空名称、同层级重复名称的提示继续沿用既有规则，不因本需求改变。
- 前端 SHOULD 在输入或失焦时展示即时校验结果，并在保存时再次校验。
- 保存失败时弹窗 MUST 保持打开，并将后端字段级错误映射到类目名称字段。

### FR-005 展示兼容性回归

- 管理端类目列表名称列 MUST 能稳定展示包含特殊字符的 15 字符类目名称，不得与编码、副行、操作列或状态列重叠。
- 管理端左侧类目树 MUST 能稳定展示包含特殊字符的类目名称；空间不足时可使用既有截断 / tooltip 策略，但不得破坏树节点层级识别。
- 管理端左侧类目树默认 MUST 只显示一级类目；有子级的一级类目前置 `+/-` 展开 / 收起控件，子级类目默认收起，展开 / 收起操作不得误触发类目筛选。
- 管理端 SKU 维护、类目选择器、筛选控件如展示类目名称，MUST 验证特殊字符不会导致搜索、选择或展示异常。
- 小程序分类页、商品列表筛选入口或 Web 展示端分类入口如直接展示类目名称，MUST 验证特殊字符名称下布局不重叠、不溢出关键容器。
- 本需求不要求所有前台端完整展示 15 个字符；若视觉空间有限，可沿用合理截断，但数据层不得拒绝合法特殊字符名称。

### FR-006 契约与测试同步

- 若 API Schema 中存在正则、枚举、校验函数或文案限制为“中文、英文和数字”，MUST 更新为支持中文、英文、数字和特殊字符。
- 若 OpenAPI 中存在 `pattern`、字段描述或错误示例表达旧字符集，MUST 同步更新。
- 若 Orval 生成客户端受 OpenAPI 影响，MUST 重新生成并提交对应生成物。
- 后端测试 MUST 覆盖包含特殊字符的类目名称可创建 / 可更新，以及最终规则禁止字符被拒绝。
- 前端表单测试 SHOULD 覆盖特殊字符名称可保存、最终规则禁止字符显示错误。
- 小程序或 Web 展示端如存在固定展示测试，应补充包含特殊字符的 15 字符样例。

## 5. UI / UE 约束

- 管理后台弹窗继续复用现有 `CategoryFormModal` 或等价 Design System 组件，不新增独立弹窗样式。
- 字段标签、必填标识、帮助文案和错误提示沿用当前管理端表单规范。
- 错误提示必须短、明确、可定位，不使用大段说明文案替代表单校验。
- 类目树、列表、选择器和前台展示入口应优先使用既有文本溢出策略；如需要新增 tooltip 或截断样式，必须遵守 semantic token 和现有组件风格。
- UI 不得因为特殊字符或 15 字符名称导致按钮、表格列、树节点、筛选控件出现文字重叠或横向撑破页面。

## 6. 数据与接口约束

- `tile_categories.name` 或等价字段的数据长度约束 MUST 支持至少 15 个用户可见字符。
- 如果数据库字段当前已支持特殊字符且无需迁移，应在实现说明中记录无需 DB migration 的原因。
- 如果数据库约束、索引、CHECK 约束或触发器当前限制为中文、英文和数字，必须通过 OpenSpec Change 明确迁移方案，并同步 SQLite / MySQL 结构文档与测试。
- 创建 / 更新类目请求体中的名称字段约束必须与 OpenAPI 一致。
- 前端不得手写与后端重复的接口类型；接口契约变化必须通过 Orval 同步。
