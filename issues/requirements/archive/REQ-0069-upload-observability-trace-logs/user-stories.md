# 用户故事

## US-001 系统管理员查看任务时间线

作为系统管理员，我希望在日志审计详情中查看一次业务任务的完整节点时间线，以便判断任务成功、失败、超时或仍在处理中。

验收要点：

- 能通过 `task_trace_id` 找到同一任务相关日志。
- 详情中能看到节点名称、顺序、耗时、状态、错误码和关联 `request_id`。
- 没有 `task_trace_id` 的普通日志仍可按现有详情展示。

## US-002 运维定位上传卡顿节点

作为开发 / 运维人员，我希望对图片、视频、文件上传按节点拆解耗时，以便定位 BUG-0085 这类 99% 停留发生在前端、后端、对象存储、数据库还是后处理。

验收要点：

- 上传任务至少记录前端上传完成、后端接收、文件校验、对象存储写入、数据库记录、响应返回等节点。
- 能识别耗时最高节点和失败节点。
- 失败节点必须关联统一错误码或失败摘要。

## US-003 运营理解长耗时任务状态

作为企业内部运营人员，我希望长耗时任务有可解释的状态，而不是只看到进度卡住或未知失败，以便减少重复提交和盲目等待。

验收要点：

- 任务状态至少覆盖 `processing`、`success`、`failed`、`timeout`、`cancelled`。
- 上传失败在上传控件内展示字段级或控件级错误，不仅依赖全局 toast。
- 任务完成后同会话能即时回显上传结果或失败原因。

## US-004 产品负责人分析慢任务体验

作为产品负责人，我希望看到关键任务耗时事实源，以便判断上传、导入、导出、发布、同步等任务后续优化优先级。

验收要点：

- 任务追踪模型不局限于上传，后续可以扩展不同 `task_type`。
- 任务摘要可以聚合为慢任务、失败任务和常见失败节点。
- 数据采集遵守权限、脱敏和保留周期。

## US-005 安全审计追溯关键操作

作为安全 / 审计负责人，我希望任务追踪能说明谁在何时发起任务、影响了什么资源，同时不泄露敏感字段。

验收要点：

- 任务记录包含操作者、客户端、资源类型、资源 ID 或脱敏资源标识。
- metadata 不保存 Authorization、Cookie、AccessKey、SecretKey、真实客户数据、内部绝对路径或完整敏感请求体。
- 管理端任务追踪查询仅系统管理员可访问。
