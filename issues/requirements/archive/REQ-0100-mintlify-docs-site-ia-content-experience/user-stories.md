# 用户故事

## US-001 公开读者从首页进入正确文档

作为店主、导购或公开访客，我希望打开文档站后先看到产品定位和常用入口，以便快速判断应该阅读小程序、公开浏览还是 FAQ。

验收要点：

- 文档站存在首页或等价首页入口。
- 首页展示平台用途、当前版本和主要角色入口。
- 首页常用任务卡片能跳转到真实存在页面。
- 首页不展示内部研发流程、OpenSpec、Issue、Sprint 或不可公开运维信息。

## US-002 企业员工按管理任务查找说明

作为企业内部员工，我希望导航按管理端使用场景组织文档，以便快速找到商品资料、品牌证书、Banner、媒体上传和账号治理说明。

验收要点：

- 当前版本导航包含管理端总览、商品资料、媒体相关和治理相关页面。
- 导航文案面向用户任务命名，而不是仅按文件目录或版本目录命名。
- 页面之间的相关手册链接有效。
- 管理端文档不暴露内部账号密码、私有域名或生产配置。

## US-003 系统管理员理解治理与权限边界

作为系统管理员，我希望文档站能清楚区分员工可用页面和管理员页面，以便培训时说明用户管理、日志审计、系统设置和接口文档入口的权限边界。

验收要点：

- 管理端治理类页面在导航中可达。
- 页面说明管理员功能和普通员工功能的访问差异。
- 文档不承诺未实现或未公开的权限模型。
- 若后续新增接口文档入口，必须明确该入口是否公开、是否仅管理员可见。

## US-004 实施和客服发送稳定版本链接

作为实施或客服人员，我希望文档站有当前版本和历史版本入口，以便给客户发送与实际系统版本一致的链接。

验收要点：

- `latest` 页面明确指向的实际版本。
- 历史版本页面路径稳定，语义不随最新版本发布而改写。
- 缺少 usage docs 的版本不生成空页面。
- 发布公告与版本使用文档都能从导航进入。

## US-005 产品负责人控制参考项目裁剪

作为产品负责人，我希望参考 ProjectDocs/promptt 和 Dify Docs 时只吸收适合瓷砖平台的文档站结构，以便避免把无关的 AI 平台、多语言、多产品线和 API 示例搬进项目。

验收要点：

- 需求和后续设计明确列出可借鉴项与不可照搬项。
- 文档站结构以“角色 + 场景 + 版本”为主。
- 不引入与瓷砖信息管理平台无关的产品线、品牌、外部域名或 analytics 配置。
- 站点级配置与文案体现本项目产品定位。

## US-006 文档维护者按事实源边界维护内容

作为文档维护者，我希望知道哪些内容来自 release 快照、哪些属于 Mintlify 体验层，以便优化首页和导航时不误改历史版本产品语义。

验收要点：

- `mintlify/README.md` 或等价治理说明记录 release 快照与站点投影关系。
- `mintlify/site-manifest.json` 或等价文件记录投影来源和人工覆盖。
- 历史版本内容性更正必须记录授权来源。
- 非内容性维护和安全修复与产品语义改写有清晰边界。

## US-007 开发和测试校验文档站质量

作为开发或测试人员，我希望有明确校验标准，以便确认 Mintlify 配置、导航、链接、图片引用和公开安全均满足上线要求。

验收要点：

- 校验能发现导航引用缺页、站内 broken links 和图片路径错误。
- 校验能发现 `.DS_Store`、构建产物或敏感信息进入 `mintlify/`。
- 校验能发现 `latest` 与 site manifest 不一致。
- 校验输出包含 blocker、warning、涉及文件和建议修复方向。
