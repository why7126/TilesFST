## Context

BUG-0084 的现象不是“视频完全不可播放”，而是“内嵌态已播放成功后，进入全屏态仍重新加载很久”。这说明基础媒体 URL、后端受控读取链路和内嵌 `<video>` 播放至少在该场景下可用，问题更集中在全屏入口的播放路径选择。

现有 SKU 详情页视频全屏能力属于 `miniapp-sku-detail-page`，其正式 spec 已要求：

- 视频由用户主动播放，不默认自动播放。
- 视频播放期间轮播不自动切换。
- 页面隐藏、锁屏、跳转时暂停当前视频。
- 视频 URL 来自后端安全可播放链路。
- 视频媒体提供全屏入口，进入微信小程序支持的视频全屏播放态。

## Goals / Non-Goals

**Goals:**

- 让已播放的内嵌视频点击全屏后尽快进入可播放全屏态。
- 优先复用当前 `<video>` / `VideoContext` 上下文，减少重新探测或重新拉流。
- 全屏失败或平台限制时提供明确反馈和可理解降级路径。
- 补充静态测试与真机证据，覆盖内嵌播放到全屏切换的耗时对比。

**Non-Goals:**

- 不在本 Change 中引入视频转码、多清晰度或 CDN 策略。
- 不默认新增后端 API、数据库字段或 Orval 生成物。
- 不绕过后端受控媒体 URL，不暴露对象存储 endpoint、bucket 或原始 object key。

## Root Cause

直接原因：小程序 SKU 详情页内嵌视频播放与全屏入口使用不同播放路径；内嵌 `<video>` 已经完成加载并可播放时，全屏入口仍可能进入独立媒体预览链路，导致重新媒体探测、拉流和缓冲。

根本原因：全屏交互设计没有把“复用当前视频组件上下文”作为主路径验收条件，缺少对已播放视频切换全屏首帧耗时的真机证据要求。

## Proposed Approach

1. **优先复用当前视频上下文**

   全屏入口应优先通过当前视频组件上下文进入全屏播放态。实现时应避免将“进入全屏”主路径绑定到会重新加载视频的独立媒体预览器。

2. **保留降级与平台边界说明**

   若微信平台能力在某些端上限制原生全屏、长按菜单或保存能力，页面应提供明确 Toast / 状态提示，并在验收材料中记录平台限制，不将不可控能力宣称为完全支持。

3. **加载反馈**

   全屏切换期间若仍发生等待，应展示可感知加载反馈或失败提示，避免用户误判为页面卡死。

4. **证据驱动验收**

   验收必须记录同一 SKU 视频的内嵌首帧耗时与全屏切换首帧耗时，确认修复确实解决 BUG-0084 的核心体验问题。

## Testing Strategy

- 小程序静态测试覆盖全屏入口使用的关键 API 或降级逻辑，并确认不再只依赖会重新加载的独立预览链路作为主路径。
- 静态测试覆盖 `index.ts` 与运行时 `index.js` 的关键逻辑同步。
- 真机 evidence 覆盖至少一个实际 SKU：内嵌播放成功、点击全屏、全屏首帧耗时、退出全屏回到当前详情页。
- 回归确认图片轮播、图片预览、收藏分享、页面隐藏暂停和安全媒体 URL 不回归。

## Risks / Trade-offs

- [Risk] 微信小程序不同基础库或机型对原生全屏 API 支持差异较大。
  - Mitigation：保留降级提示，并在验收材料中记录平台边界。
- [Risk] 若视频文件本身很大或编码不适合移动端，全屏切换仍可能有短暂等待。
  - Mitigation：验收记录视频大小、编码、网络和耗时，避免混淆全屏路径问题与素材性能问题。
- [Risk] 当前已有视频全屏操作菜单相关测试可能绑定旧实现。
  - Mitigation：更新测试表达用户目标和平台边界，而不是固定旧 API。
