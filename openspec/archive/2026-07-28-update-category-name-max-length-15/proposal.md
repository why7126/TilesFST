## Why

管理端类目名称当前存在最多 10 个字符的实现或验收假设，部分瓷砖类目需要更完整的业务命名，10 字符容易迫使运营使用缩写并降低分类可读性。需要将类目名称业务输入上限统一放宽到 15 个字符，并把前端、后端、OpenAPI/Orval、测试与展示回归纳入同一变更闭环。

## What Changes

- 类目名称创建 / 编辑的业务输入上限调整为 15 个用户可见字符。
- 前端表单与后端 API 兜底都必须接受 1-15 字符名称，并拒绝 16 字符及以上名称。
- 超长错误提示统一表达为「类目名称最多 15 个字符」或等价文案。
- 保持既有字符集、同层级唯一、编码自动生成、层级、排序权重和启停删除规则不变。
- 同步 OpenAPI / Orval / docs / tests 中的长度约束与测试夹具。
- 回归管理端类目列表、类目树、小程序分类页和 Web 展示端分类入口的 15 字符展示兼容性。

## Capabilities

### New Capabilities

- 无。

### Modified Capabilities

- `tile-category-management`: 类目名称创建 / 更新输入规则新增 1-15 字符业务上限，并要求 API、表单校验和展示回归保持一致。

## Impact

- 后端/API：影响管理端类目创建与更新接口的 Pydantic Schema 或业务校验、错误响应、测试。
- Web 管理端：影响 `CategoryFormModal` 类目名称本地校验、错误提示、类目树和列表展示回归。
- 小程序 / Web 展示端：不新增能力，但需使用 15 字符类目名称样例回归分类入口布局。
- 数据库：需确认 `tile_categories.name` 支持至少 15 个用户可见字符；仅当发现 10 字符约束时需要迁移。
- OpenAPI / Orval：如 schema 暴露 `maxLength`，必须更新并重新生成客户端。
- 不影响对象存储、媒体上传、认证授权、Docker Compose 或环境变量。
