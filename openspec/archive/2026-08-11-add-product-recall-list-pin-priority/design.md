# 设计说明

## 1. 设计目标

本 Change 的设计目标是在不改变小程序视觉和榜单语义的前提下，为少量运营配置的召回 SKU 提供稳定、可测试、分页前生效的排序优先级。排序事实源在后端，小程序端只渲染接口返回顺序。

## 2. 数据模型

在 `tiles` 表新增或等价维护以下字段：

| 字段 | 语义 | 约束 |
|---|---|---|
| `recall_pin_sort_order` | 召回置顶排序值 | 正整数，默认 `9999`，数值越低越靠前；`9999` 视为普通商品。 |
| `recall_pin_starts_at` | 生效开始时间 | 可为空；为空表示立即可生效。 |
| `recall_pin_ends_at` | 生效结束时间 | 可为空；为空表示长期有效。 |

有效期判断使用服务端当前时间。若开始时间和结束时间均为空，则仅当 `recall_pin_sort_order < 9999` 时视为长期生效置顶。若开始时间晚于结束时间，管理端保存 MUST 被字段级校验拒绝。

SQLite 与 MySQL schema、migration、baseline 和数据库文档 MUST 保持字段语义一致。查询路径 SHOULD 为公开列表排序补充组合索引或等价优化，至少避免因召回字段导致公开 SKU 列表显著退化。

## 3. 排序策略

后端在品牌、分类、普通关键词商品列表和搜索 SKU 结果中按以下顺序处理：

1. 先应用既有公开条件过滤：SKU 已上架、品牌启用、类目启用、规格可用等。
2. 再应用当前请求筛选：关键词、品牌、类目、规格、价格区间等。
3. 再计算当前请求内的生效召回候选：`recall_pin_sort_order` 为 `1..9998`，且当前时间在有效期内。
4. 每次请求最多让 4 个生效召回候选进入置顶区；超出时按 `recall_pin_sort_order` 升序、既有排序兜底、SKU ID 升序裁定。
5. 置顶区排在普通区之前；普通区继续使用对应列表原有排序。
6. 排序必须在分页前对完整结果集生效。

同一排序值的召回 SKU 使用既有列表排序和 SKU ID 作为稳定兜底，保证刷新、翻页和加载更多不重复、不漏项、不跳动。

以下分支 MUST 跳过召回置顶排序：

- 新品榜：`section=new` 或等价新品入口。
- 热销榜：`section=hot` 或等价热销入口。
- 价格升序 / 降序等显式价格排序分支。
- 首页无筛选全部产品瀑布流，继续保持既有首页排序。
- 收藏列表、搜索实时联想、管理端 SKU 列表、店主 Web 商品列表。

## 4. API 与 Schema

管理端 SKU create/update/detail 响应 SHOULD 暴露召回置顶配置字段，便于保存回显。若管理端列表需要编辑入口回显，也 MAY 在列表项中返回这些字段，但列表排序不得改变。

小程序公开商品卡片响应不需要返回召回状态或置顶标识字段。若为了后端测试或调试需要内部解释字段，必须限制在测试或内部日志中，不进入小程序公开 Schema。

字段变更后 MUST 同步 Pydantic Schema、OpenAPI、Orval 和接口文档；请求校验失败沿用统一错误响应，正整数或时间范围错误可使用现有参数校验错误码或在实现阶段补充明确错误码。

## 5. 管理端 UI 策略

D1 UI 策略：采用 Design System / 现有 SKU 弹窗复用策略。管理端在 SKU 新建 / 编辑弹窗中加入：

- `InputNumber`：标签为“排序”，放在参考价格之后，标记必填，默认 `9999`，仅允许正整数。
- 帮助图标：排序标签旁显示问号图标，hover 时说明默认值、正整数约束和数值越低越靠前。
- `DateTimePicker`：生效开始时间。
- `DateTimePicker`：生效结束时间。

排序字段校验失败时，错误提示必须展示在排序输入框下方，使用红色字段级提示文案“排序值必须为正整数”，不得挤占弹窗顶部全局错误区。管理端 SKU 列表在状态字段前展示“排序”字段，用于查看当前召回排序配置，但列表默认排序不得因该字段改变；状态字段中的“已上架”“已下架”等短标签必须保持单行显示。保存成功或失败反馈使用现有 fixed toast；弹窗主体保持矮视口可滚动、头尾固定可见，并避免同时挂载 `modal-card` 与专属弹窗类。若后续实现新增独立运营配置页，必须补充原型或截图验收材料。

## 6. 小程序 UI 策略

小程序不新增视觉稿、不新增卡片角标、不新增排序说明、不新增搜索 / 筛选 / 排序控件。品牌、分类、普通关键词商品列表和搜索结果中的商品卡片继续复用现有结构，只体现后端返回顺序；首页无筛选全部产品瀑布流继续保持既有首页排序。

## 7. 原型与冲突处理

Conflict Report：

- HTML 原型：无。
- PNG Golden Reference：无。
- `prototype/web/context.md`：要求管理端 SKU 维护入口增加运营配置字段，小程序不新增 UI 标识。
- `acceptance.md`：与 context 一致，并补充分页、筛选、榜单例外和测试要求。
- `rules/ui-design.md` 与既有 `tile-sku-management` 规格：要求复用 Design System 与 SKU 弹窗可滚动验收。

Conflict Resolution：采用 `prototype/web/context.md` 与 `acceptance.md` 的共同口径；小程序无 UI 改动，管理端仅复用 SKU 弹窗现有表单能力补充字段组。无需要从 HTML / PNG 消化的冲突。

## 8. 风险与控制

| 风险 | 控制 |
|---|---|
| 置顶只在当前页内排序导致翻页重复 | 后端必须分页前排序，测试覆盖多页加载。 |
| 召回商品越过筛选条件 | 排序资格在公开过滤和请求筛选之后计算。 |
| 榜单语义被覆盖 | `section=new`、`section=hot` 和价格排序分支加回归测试。 |
| 运营配置过多导致列表被占满 | 每次请求最多 4 个生效置顶 SKU。 |
| 字段兼容不一致 | SQLite / MySQL / Pydantic / OpenAPI / Orval / docs 同步校验。 |
