## Why

管理后台瓷砖类目名称当前规则为“最多 15 个字符，只能包含中文、英文和数字”，但运营在维护真实瓷砖分类时经常需要使用连接符、斜杠、括号、点号等特殊字符表达系列、组合、规格或场景。需要在保持 15 字符长度上限不变的前提下，放宽类目名称字符集，并让前端、后端、OpenAPI / Orval、测试和展示回归保持一致。

## What Changes

- 类目名称创建 / 编辑的业务输入规则调整为最多 15 个用户可见字符，允许中文、英文、数字和常见可见特殊字符。
- 前端表单与后端 API 兜底都必须接受合法特殊字符名称，并拒绝空名称、16 字符名称、换行、制表符和不可见控制字符。
- 非法字符错误提示统一表达为“类目名称仅支持中文、英文、数字和特殊字符”或等价产品确认文案。
- 保持同层级唯一、编码自动生成、层级、排序权重、启停和删除规则不变。
- 同步 OpenAPI / Orval / docs / tests 中的字符集约束与测试夹具。
- 回归管理端类目列表、类目树、类目选择器、小程序分类页和 Web 展示端分类入口的特殊字符展示兼容性。

## Capabilities

### New Capabilities

- 无。

### Modified Capabilities

- `tile-category-management`: 类目名称创建 / 更新输入规则在 15 字符业务上限基础上放宽字符集，支持中文、英文、数字和常见可见特殊字符，并要求 API、表单校验和展示回归保持一致。

## Impact

- 后端/API：影响管理端类目创建与更新接口的 Pydantic Schema 或业务校验、错误响应、OpenAPI schema 和测试。
- Web 管理端：影响 `CategoryFormModal` 或等价类目表单的本地校验、错误提示、类目树、列表和选择器展示回归。
- 小程序 / Web 展示端：不新增能力，但需使用特殊字符类目名称样例回归分类入口布局与筛选行为。
- 数据库：需确认 `tile_categories.name` 支持特殊字符；仅当发现数据库 CHECK / 触发器等真实字符集约束时需要迁移。
- OpenAPI / Orval：如 schema 暴露 `pattern` 或字段描述，必须更新并重新生成客户端。
- 不影响对象存储、媒体上传、Docker Compose 或环境变量。
