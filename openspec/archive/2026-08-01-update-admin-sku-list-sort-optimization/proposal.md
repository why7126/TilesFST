## Why

管理端 SKU 列表当前正式规格要求“已发布 SKU 优先”，但 `REQ-0087` 已评审确认新的运营优先级：未上架 SKU 需要优先出现，便于运营先处理待完善、待发布或已下架后需要复核的商品。若继续沿用已发布优先，运营仍需额外筛选或翻页才能找到待处理 SKU。

## What Changes

- 调整管理端 SKU 列表默认排序契约：未上架 SKU 排在已上架 SKU 之前。
- 未上架 SKU 分组内按 `created_at` 降序排列，最新创建的 SKU 排在前面。
- 已上架 SKU 分组内按 `published_at` 降序排列，最新发布的 SKU 排在前面。
- 明确时间为空或重复时必须使用稳定兜底排序，避免分页、刷新或重复请求后顺序跳动。
- 搜索、品牌筛选、类目筛选、状态筛选、素材完整度筛选和分页后仍必须保持该排序契约。
- 不新增显式排序控件、筛选项、发布流程改造、数据库结构或公开端排序变化。

## Capabilities

### New Capabilities

- 无。

### Modified Capabilities

- `tile-sku-management`: 修改管理端 SKU 列表默认排序契约，从“已发布优先”调整为“未上架优先；未上架按创建时间降序；已上架按发布时间降序”。

## Impact

- 影响范围：管理端 SKU 列表后端查询排序、管理端 Web 列表刷新/分页后的展示顺序。
- API：可能不新增字段，但若实现新增排序参数、派生字段或响应字段，必须同步 Pydantic Schema、OpenAPI、Orval、接口文档和测试。
- 数据库：通常不需要结构变更；需确认 `status`、`created_at`、`published_at` 支持排序。
- 管理端 Web：保持现有列表结构、筛选区、分页、状态标签、操作列和加载/空态/失败态。
- 小程序 / 店主 Web / MinIO：不涉及。
- 测试：需要补充或更新后端 pytest 与前端 Vitest/Testing Library，覆盖分组排序、时间排序、空值兜底、筛选分页稳定性。

## Rollback Plan

如排序优化导致运营侧列表顺序异常、分页重复漏项或组合筛选回归，可回退本 Change 的后端/前端排序实现，恢复当前 `tile-sku-management` 排序契约。回退不得修改 SKU 状态、发布时间或创建时间数据；回退后需重新评估 `REQ-0087` 是否调整验收或拆分后续修复。
