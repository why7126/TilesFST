## 背景

`BUG-0132` 记录了微信小程序商品详情页冷加载图片耗时异常：用户在开发者工具 Network 中补充了多组商品详情页请求证据，冷加载阶段出现 `1.1 MB` JPEG 约 `6.04 s`、`1.5 MB` PNG 约 `5.24 s`、`3.6 MB` PNG 约 `11.10 s`、`826 kB` JPEG 约 `5.68 s` 等大图请求。该问题会拖慢详情页首屏和普通浏览体验，且在 `Disable cache`、移动网络或后端 `/media` 代理路径下影响更明显。

`BUG-0132` 已评审通过并纳入 `sprint-025`。本 Change 聚焦缺陷修复：限制详情页冷加载默认展示链路中的大图资源，保证高清原图只在用户点击预览时加载。通用媒体多规格建设由 `REQ-0115` 对应 Change 承接，本 Change 只约束详情页修复所需的最小行为边界。

## 变更内容

- 调整小程序商品详情页图片 URL 选择策略：普通展示优先使用详情展示图或安全压缩图，高清原图只用于点击预览。
- 限制详情页默认冷加载大图：普通展示链路不得默认加载 `>1 MB` 原图；首屏关键图片目标控制在 `100-300 kB`；普通详情展示图目标控制在 `150-500 kB`。
- 明确 PNG 大图治理：大 PNG 必须存在展示版替代；非透明 PNG 可转换为 JPG 或 WebP 等展示格式。
- 详情页首屏外图片启用 `lazy-load` 或等价延迟加载，降低冷加载并发压力。
- 若后端 API 当前缺少可区分展示图与预览原图的字段，需要补齐等价字段或安全 fallback，并同步 OpenAPI、Orval、文档和测试。
- 验收阶段必须补充小程序 Network evidence，覆盖资源大小、耗时、Waterfall、展示 URL 与预览 URL 的区别，并保留媒体 key、object、URL、render 四点证据。

## 影响范围

- 后端：可能影响 SKU 详情媒体组装、媒体 URL 选择、展示图 fallback 和 `/media` 代理返回策略。
- API：若新增或调整 `display_url`、`preview_url`、`original_url` 等字段，需要同步 OpenAPI、Orval 和 API 文档。
- 数据库：默认不要求结构变更；如实现选择持久化派生图关系，必须同步 schema、迁移、数据库文档和测试。
- 对象存储：需要保持原图与展示图对象可追溯，且不得向小程序暴露未授权 object key、bucket、endpoint 或内部路径。
- 微信小程序：影响商品详情页图片展示、点击预览、首屏外图片 lazy-load 和 Network 验收。
- Web 管理端：默认不改 UI；如需要上传后生成或回填展示图，需与 `REQ-0115` 的通用媒体多规格能力保持一致。

## 回滚计划

- 若详情展示图选择导致图片清晰度或兼容性问题，可临时回退到修复前展示 URL 选择，但必须保留 `BUG-0132` 为 reopened 或 follow-up 状态，不得声明已修复。
- 若 lazy-load 在目标基础库或真机上引发渲染异常，可先仅保留首屏外非关键图的延迟加载开关，并记录具体机型、基础库版本和 Network 证据。
- 若 API 字段变更影响客户端兼容，可保留旧字段并新增等价展示字段，待小程序切换完成后再清理旧字段。
- 回滚不删除原图或派生图对象，不做破坏性数据清理。
