## 背景

项目已具备对象存储单桶策略、媒体多规格图片能力和生产媒体维护作业规范，但批量图片处理操作仍缺少一份面向执行者的 Runbook。REQ-0122 要求该 Runbook 同时服务研发、运维、验收和版本交付，因此需要把长期事实源与版本快照投影一起纳入设计。

## 目标与非目标

目标：

- 建立一份可执行的批量图片处理 Runbook，覆盖脚本清单、执行顺序、参数边界、风险门禁和验收证据。
- 将 Runbook 同步投影到 `docs/` 长期事实源和 `releases/vX.Y.Z/usage-docs/` 版本快照，避免只在单一目录可见。
- 明确 `thumb` / `display` 派生生成、缩略图专项重建和对象 key 迁移的 dry-run/apply、安全、回滚与审计要求。

非目标：

- 不在本 Change 直接执行生产图片处理、对象 key 迁移或历史数据修复。
- 不改变现有 API 字段、数据库表结构、对象存储单桶策略或多端图片消费矩阵。
- 不把尚未存在或未验证的脚本描述为生产可直接 apply。

## 关键决策

1. Runbook 使用双投影归属。

   长期事实源落在 `docs/` 下，由版本化使用文档快照投影到 `releases/vX.Y.Z/usage-docs/`。这样可以让研发持续维护同一份知识，同时让每个发布版本保留与交付包一致的执行说明。

2. 脚本清单按状态分层。

   Runbook 必须区分“现有可用脚本”“需修改脚本”“新增脚本或待实现入口”。未实现脚本只能写成规划或待办，不能给出生产 apply 命令，避免运维误执行不存在或未验证的入口。

   生产推荐命令使用语义化任务名。历史来源可继续记录 `BUG-*`，但执行者复制的聚合任务名应使用 `media-drift-reconcile`；旧 `bug-0116-media-drift` 仅保留为兼容别名，避免把一次缺陷编号固化成长期运维接口。

3. 生产步骤以 dry-run / apply / audit 三段组织。

   每类批量任务都先 dry-run 输出脱敏摘要，再在数据库快照和 bucket / prefix 快照确认后显式 apply，最后执行二次审计并记录 key、object、URL、render、benefit 等证据。

4. 对象 key 迁移回滚以快照恢复为准。

   对象 key 迁移涉及数据库引用和对象存储内容一致性。除非实现阶段提供并验证反向脚本，否则 Runbook 必须把数据库快照和 bucket / prefix 快照恢复描述为默认回滚路径。

## 风险与缓解

- 脚本状态被误读为已实现 → Runbook 使用状态列、前置条件和禁用 apply 示例区分可执行与待实现。
- 生产命令泄露敏感信息 → 命令示例只使用变量名和占位符，验收要求脱敏输出，不记录 `.env`、密钥、Cookie、Authorization header、本机绝对路径或真实客户数据。
- 迁移失败造成数据库与对象存储不一致 → apply 前要求 MySQL 快照与 bucket / prefix 快照，apply 后要求幂等审计和失败清单。
- 双投影漂移 → 实现阶段需在 manifest 或版本文档索引中记录源文档路径、快照路径、更新时间和差异检查结果。

## 迁移计划

本变更不迁移生产数据。实现完成后，首次版本发布时将 Runbook 从长期事实源投影到对应 `releases/vX.Y.Z/usage-docs/` 快照，并通过 usage-docs 校验或等价文档校验证明快照存在。

## 未决问题

- 首次承载该 Runbook 的具体版本号需在实现或发布计划中确认。
- 若实现阶段发现现有脚本缺口，需决定是在本 Change 内补脚本，还是拆出后续 REQ/BUG/Change。
