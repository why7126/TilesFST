## Context

`REQ-0083-miniapp-brand-list-category-summary` 是 `REQ-0060-brand-list-page` 的体验增强。当前正式 spec `miniapp-brand-list-page` 要求品牌列表页下半部以一行 2 个品牌卡片展示公开品牌；本需求要求保留顶部品牌轮播不变，将下半部改为每行一个品牌，并在同一行展示品牌 Logo、品牌名称、公开商品数量和该品牌公开商品对应的末级类目名称集合。

当前约束：

- 品牌列表页顶部轮播仍遵守现有品牌列表页轮播、Banner 位置隔离和安全 URL 规则。
- 小程序端不得直连未授权对象存储或管理端私有接口。
- 如公开品牌列表接口缺少 `productCount` 或 `leafCategoryNames`，需要扩展公开 API 契约并同步 OpenAPI、Orval 或小程序 API 类型、接口文档与测试。
- 小程序导航、胶囊避让、DevTools/真机 evidence 继续引用 `docs/knowledge-base/best-practices/miniapp-custom-navigation.md`。

## Goals / Non-Goals

**Goals:**

- 将品牌列表页下半部改为单行品牌信息布局。
- 左侧展示品牌 Logo、品牌名称和公开商品数量。
- 右侧展示该品牌公开商品的末级类目名称集合，并去重。
- 明确商品数量和末级类目集合使用同一公开商品口径。
- 继续保留品牌行点击跳转、不可用品牌降级、埋点脱敏和设备 evidence 门禁。

**Non-Goals:**

- 不修改品牌列表页顶部轮播视觉、数据来源、跳转或兜底规则。
- 不改造品牌主页/详情页。
- 不新增品牌搜索、类目筛选、收藏、询价或下单流程。
- 不新增品牌、SKU 或类目数据库表。
- 不改造管理端品牌维护、商品类目绑定或类目管理流程。
- 不影响 Web 展示端或管理端 UI。

## Decisions

### D1. 用 `update` 修改既有品牌列表页能力

正式 spec 已有 `miniapp-brand-list-page`，且现有 “双列品牌卡片列表” 与本需求直接冲突。因此本 Change 使用 `update` 类型，delta spec 在 `MODIFIED Requirements` 中完整替换相关 Requirement，而不是新增平行 Requirement。

备选方案：新增 `miniapp-brand-category-summary` 能力。该方案会让“品牌列表页到底显示双列卡片还是单行汇总”分散在两个能力中，归档后容易冲突，因此不采用。

### D2. 单行品牌信息保留整行点击语义

品牌行不再是双列品牌卡片，但用户心智仍是点击某个品牌继续进入品牌主页/详情页或品牌商品列表。因此实现应保留整行点击区域和现有跳转上下文，包括品牌 ID、品牌名称、来源页面和位置索引。

备选方案：只让品牌名称或 Logo 可点击。该方案触控范围小，不适合小程序移动端扫读，因此不采用。

### D3. 商品数量与末级类目集合使用同一公开商品集合

`productCount`、`leafCategoryNames` 与 `leafCategories` 必须基于相同的“小程序公开可见商品”集合计算。`leafCategories` 需要包含末级类目 ID 与名称，供右侧类目点击跳转到品牌 + 类目商品列表页；`leafCategoryNames` 作为名称集合兼容展示。这样可避免出现数量与类目不一致的体验问题，例如数量为 0 但仍展示类目，或有商品数量但右侧类目无解释。品牌无公开商品时左侧商品数量已展示空态值，右侧类目区留空，不重复展示“暂无商品”。

实现阶段若现有接口无法提供该聚合，后端应在公开品牌列表查询中聚合公开 SKU 及其类目路径，过滤未公开、停用或不应展示的数据。

### D4. 末级类目展示采用去重 + 稳定排序 + 全量折行

右侧类目集合必须去重。排序优先使用类目后台排序；若接口暂不提供排序依据，则必须在实现设计或代码中选择稳定兜底排序，避免列表刷新后顺序抖动。品牌行右侧必须展示品牌下所有上架/公开商品关联的末级类目名称，小程序端不得使用数量上限、`+N` 或“等 N 类”折叠隐藏后续类目；类目较多时通过折行和品牌行自适应高度承载，并必须满足 320/375/430 pt 不横向滚动和不遮挡左侧品牌信息。

### D5. 原型与验收冲突解决

原型优先级：

```text
prototype/miniapp/prototype.html > prototype/miniapp/context.md > acceptance.md > rules/ui-design.md > openspec/specs
```

Conflict Resolution：

- 现有正式 spec 的“双列品牌卡片”与 `REQ-0083` 原型和验收冲突，以 `REQ-0083` 原型和验收为准，delta spec 将其修改为单行品牌信息布局。
- 顶部轮播相关 spec 与 `REQ-0083` 不冲突，保持不变。
- 小程序导航与设备 evidence 既有 spec 仍适用，但验收描述需从“双列品牌卡片”调整为“品牌单行列表”。

## Risks / Trade-offs

- [Risk] 公开品牌列表接口当前可能缺少商品数量和末级类目集合 → Mitigation: tasks 中先确认接口契约；缺字段时同步扩展 API、OpenAPI/Orval 或小程序 API 类型和测试。
- [Risk] 品牌下类目过多导致右侧拥挤 → Mitigation: 小程序 UI 使用折行与品牌行自适应高度展示全部类目，并在 320/375/430 pt 验收。
- [Risk] 商品数量与类目集合口径不一致 → Mitigation: 后端或小程序数据聚合必须共用同一公开商品过滤条件，并补测试覆盖。
- [Risk] 顶部轮播被列表改版误改 → Mitigation: spec 和 tasks 明确轮播不属于本次改造，并要求回归现有轮播交互。

## Migration Plan

1. 确认小程序品牌列表页当前数据来源和响应字段。
2. 如缺少聚合字段，扩展公开品牌列表接口并同步契约与测试。
3. 调整小程序品牌列表页下半部渲染为单行品牌信息布局。
4. 保留顶部轮播、跳转、埋点、加载/空/错态和安全过滤。
5. 品牌 Logo / 名称点击进入品牌详情页；右侧类目点击进入该品牌该类目下的商品列表页。
6. 运行后端、API 契约、小程序静态/页面验证和设备 evidence 记录。

回滚策略：保留原品牌列表页数据加载与跳转入口；若单行汇总出现阻断问题，可临时回退到旧列表组件，但不得同时展示双列卡片与单行汇总两套互相冲突的列表。

## Open Questions

- 末级类目展示上限已在验收返修中确认取消；小程序端展示全部去重末级类目，不使用 `+N` 或“等 N 类”折叠。
- 当前公开品牌列表接口是否已返回可直接使用的品牌公开商品数量和末级类目集合。
